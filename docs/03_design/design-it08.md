## 2. 改行のない貼り付け（DES-RCP-09）

### 2.1 分割

元の物理行を CRLF または LF で分け、1 始まりの物理行番号を割り当てる。各行を NFKC 正規化し、前後の空白と従来の行頭記号（`•` を含む）を除く。文字数は NFKC 後の UTF-16 コード単位で数える。正規化後の物理行が 4000 文字を超えたら分割も解析もせず、元行全体を 1 件の登録しない物とする。

その後、従来の桁区切り除去 ` (\d),(?=\d{3}(?:\D|$)) `（前後の空白は式に含まない）を物理行全体に適用する。結果を半角空白・タブの連続で区切り、トークンを左から一度ずつ走査する。名前は空でなく半角コンマを含まず、空白を含んでもよい。コンマを含まないトークンを名前の一部として蓄え、コンマを 1 個だけ含むトークンではコンマ前を名前の末尾、直後からトークン末尾までを量とする。量は符号付きの数値（小数・分数）と直後に空白なく続く任意の既存単位・g・kg・ml、または単位なしの数値全体に一致すること。コンマ前が空でも蓄えた名前があればよい。組を確定したら蓄積を空にする。余分なコンマ、不正な量、末尾の余りがある場合、または組が 1 個以下の場合は分割せず、200 文字以内なら従来の 1 行解析へ渡す（従来の数値と単位の間の `\s*` は維持）。この処理は入力長に線形で、行全体に後戻りする正規表現を使わない。

2 組以上に分割できた場合、各組の長さを桁区切り除去後・前後の境界空白を除いた文字列で測り、いずれかが 200 文字を超えたら行全体を 1 件の登録しない物とする。分割できない 200 文字超の行も同様とする。分割後の組は元の順で個別に解析する。2 組目以降の先頭の `•`・`-`・`*`・`・`・`1.` は除かず名前の一部とする。組の途中の記号を箇条書きと断定せず、特に負号を失わないためである。

例えば `A,1 B,2 C,3` は 3 組、`豚肉,1 個 鶏卵,1` は「豚肉,1」「個 鶏卵,1」、`豚肉,1,000g 鶏卵,1` は桁区切り除去後に 2 組、`豚肉,1 • 鶏卵,1` の 2 組目の名前は `• 鶏卵`。`豚肉 300g` と `ロース ハム,1` は従来の 1 行解析に渡す。一致の有無は分割位置に影響しない。

分割した候補・登録しない物には物理行番号と 1 始まりの行内順を付ける。分割しなかった行の行内順は持たせない。確認一覧の React key は行番号と行内順の組（非分割は順 1）とし、分割した候補の登録・量・単位などの読み上げ名は「3 行目の 2 品目を登録する」「3 行目の 2 品目の量の単位」のように区別する。非分割は従来の文言を維持する。未一致の表示は組の原文、非分割は元行とする。読み取り時の重複食材は別候補とし、登録時は従来の DES-RCP-05 どおり同じ食材を加算する。

空白だけで分ける案は商品名や `豚肉 300g` を壊すため採らない。コンマのない複数組の推測や部分的な救済はしない。

### 2.2 指示文

DES-RCP-02 の形式の指示を「必ず食材 1 品ごとに改行し、1 行に 1 品だけを『食材名,量』の形で書いてください。複数の品を空白でつないで 1 行に書かないでください。」に置き換え、既存の重量・個数・小数の指示は維持する。コピー方法で改行が失われる場合もあるため、指示強化だけには依存しない。

## 3. 読み取りの残り（DES-RCP-10）

- `1/2個` のように既存の個数単位、g・kg・ml を分数の後に付けられる。分母 0、非有限値は既存の不正量と同様に個数 1・要確認とし、分数は丸めの有無にかかわらず要確認とする。既存の個数の 0.5 刻み・上限、重さの整数 g・範囲と要確認の規則を適用する。
- 負号は NFKC 後の `-` と `−`（U+2212）を認める。行頭の `•` を既存の `-`・`*`・`・` と同様に除く。負号を箇条書きと誤認しないよう、量部分の符号は除かない。
- ml は対象を食材名で限定せず、貼り付けで明示された体積だけを **1 ml ≒ 1 g の概算**として購入時重量に換算し、整数 g に丸め、範囲制限も既存の重量と同じにする。密度は食品で異なるため常に要確認とし、確認画面で「ml を 1 ml ≒ 1 g の概算で換算しました。重さを確認してください」と示す。`ReceiptCandidate` に ml 換算由来の真偽値を追加し、既存の「量を確かめてください」と並べて表示する。`ml` は `mL`・`ML` を含め大小文字を区別しない。係数のコード定数の近くに「外部資料ではない概算、本人の査閲待ち」と記す。保存は既存の g の重量で、ml の表示単位や食品別密度は追加しない。この係数は外部資料による実測値ではなくエージェントの簡易な仮定で、本人の査閲を要する。
- 明示的な負の量（`-1`、`-1/2個`、`-200ml` など）は一致する食材でも候補にせず、その組を登録しない物に回す。負号を落として正の量にしない。0 とその他の不正値は既存の要確認の扱いを維持する。

食品ごとの密度表は根拠と対象の査閲が必要で今回作らない。負の量を 1 にして候補にする案は値引き行の誤登録を招くため採らない。複数組からも同じ規則で負の量を認識する。

## 4. 少ない登録の案内（DES-BAL-08）

`analyzeBasket` が判定に使う `active` の行数を judged 結果にも渡す。正の量かつエネルギー値が null でない登録行を数え、同名でも別行なら別に数える。設定で自動追加する主食は含めない。これは既存の最低 3 品目の数え方と揃えるためで、食品の種類数ではない。判定できた場合に限り、3 または 4 行なら案内し、5 行以上と未判定では出さない。境目 5 は E-146 の例を採用したエージェントの判断であり、根拠ある栄養学上の閾値ではない。

ホームと前の買い物の `BalancePanel` の判定見出し直下に「登録した食材が少ないため、判定は登録した食材と設定した主食に基づく目安です。」と表示する。主食なしの場合の案内全文は「登録した食材が少ないため、判定は登録した食材に基づく目安です。」とする。栄養詳細には追加しない。判定の入口で伝え、対象外の判定画面の改修を広げないため。常時表示や主食を品数に加える案は、少ない登録への注意を曖昧にするため採らない。多品数でも肉・卵に偏る例には案内が出ないことを H-20 の結果と分けて記録する。

## 5. ホームの食材行（DES-UI-52）

閉じた行は `［食材名（開閉）］ ［−］ ［量］ ［＋］` の横 1 行とする。名前領域は独立したボタンで、押すと行内の詳細を開閉する。個数は従来どおり 0.5 刻み、最小・最大では該当ボタンを無効にする。個数の量にも単位（例: `1.5 つ（概算）`）を含める。重さの場合は量と単位を表示し、増減ボタンは表示せず、編集は詳細に置く。行全体をボタンにせず、増減操作が開閉を起こさないようにする。

同名行が複数ある場合の詳細名（`detailOf`）は閉じた行でも名前の下に小さく表示し、省略可能とする。完全な詳細名を名前・増減の読み上げ名に含める。名前領域は詳細名を含め 44 × 44 CSS px 以上とし、2 行の文字が収まる高さを確保する。

開いた詳細に目安重量、個・g・kg の切り替え、重さ入力とエラー、削除を置く。既存の換算、重さ確定、無効入力、切り替え後の焦点（DES-UI-51）と削除取り消しを保つ。詳細を閉じる際に未確定の重さを検証・確定し、無効なら開いたまま入力欄へ焦点を戻す。削除後は既存の取り消し通知へ焦点を移す。ホームと前の買い物の双方で、取り消し後は復元行を閉じた状態で表示し、個数行は既存どおり有効な増減ボタン、重さ行は名前の開閉ボタンへ焦点を移す。開閉状態は画面内の一時状態で保存しない。

名前ボタンに食材名と「詳細を開く／閉じる」の読み上げ名、`aria-expanded` と対応する領域の `aria-controls` を付け、Tab・Enter・Space で操作する。増減・単位・削除にも食材名を含む既存の名前を保つ。閉じた領域はフォーカス対象にしない。360 CSS px で名前領域を縮めて省略表示し、完全な名前は読み上げ名と開いた詳細で確認できるようにする。各操作領域は 44 × 44 CSS px 以上、横スクロールなし。長い量・名前を含む実寸で確認する。

同じ `ItemRow` を使う前の買い物の詳細にも同じ操作を適用し、その買い物だけを変更する。登録画面は既に食材名の 1 押し登録があり、ホームから 3 タップ以内を満たすため変更しない。使い切りは追加しない（E-149）。行の `memo` と画面外描画の最適化を維持し、推定高さを新しい行の実寸に合わせて見直す。CPU 4 倍・100 行で登録、増減、削除から判定更新まで NFR-03 の 100 ms を再計測する。

## 6. 共通の検証と互換性

core は純粋関数のまま表駆動単体テストを追加し、網羅率・型・lint を維持する。保存形式は変えず既存データを読む。画面は mobile / desktop、360 px、閉じた状態と開いた状態で寸法・axe の重大違反 0・キーボード・読み上げ名を検査する。既存の登録・履歴・重さ・削除・性能 E2E も維持し、操作位置の変化に合わせる。CI の性能時間超過は既存方針どおり記録のみ、計測不能・機能不整合は失敗とする。

## 9. レビューで確かめる点・計画・要求への提案

以下はエージェントの設計判断であり、本人の指示や承認ではない。計画・要求への変更提案はない。

- 4000 文字の物理行と組ごとの 200 文字は処理量を抑えつつ改行なしの多数品に対応する設計上の上限で、外部資料による数値ではない。超過行は全体を登録しないため、H-19 の検証では長い実入力の文字数と未登録を記録する。上限なしの案は処理量を制限できず採らない。
- `−` も負号とするのは貼り付けで現れる符号を安全に拒否するため。`-` のみとする案では `−` を含む複数組の分割が崩れる。
- 個数単位は既存の目安単位で数えるため、目安が 1/4 個のかぼちゃでは `1/2個` は 0.5 目安単位（実物の 1/8 個）となる。既存の `1個` も同じ限界があり、要確認を付ける。単位ごとの換算表は今回作らない。
- 主食ありの文言は実際に設定した主食も判定に足されるため、FR-BAL-09 の「登録した食材だけ」をその事実に合わせて解釈した。主食に言及しない案もある。境目 5 と両文言を H-20 で本人に確かめる。
- FR-UI-10 の「行を押して開く」は名前の領域を押す操作と解釈した。行全体を開閉にすると増減との操作が競合するため。閉じた行の詳細名と 44 px の操作領域に必要な高さは実測する。
- ml の係数は食品ごとの正確な密度ではない概算で、本人の査閲が必要。食品別の密度表は根拠と査閲が必要なため採らない。
