## 2. 補う候補（DES-SUG、`src/core/suggestions.ts`）

### 2.1 入出力（DES-SUG-01）

```ts
type SupplementCandidate = {
  food: FoodItem;
  displayName: string;
  priority: number;
};
type SupplementSuggestion = {
  foodId: string;
  displayName: string;
  improvedKeys: NutrientKey[];
  improvement: number;
  newHighKeys: NutrientKey[];
  newLowKeys: NutrientKey[];
  worsenedHighKeys: NutrientKey[];
  approximate: boolean;
};

supplementCandidates(foods: FoodItem[]): SupplementCandidate[];
suggestSupplements(
  state: AppState,
  foodsById: ReadonlyMap<string, FoodItem>,
  candidates: SupplementCandidate[],
  data?: AnalysisData,
): SupplementSuggestion[];
```

- `supplementCandidates` は `isRegistrable` → `groupFoods` → `supermarketPriority(group.name) !== null` → `representativeFood` の順で選ぶ。未検索時の画面の先頭 80 件には制限しない。食品番号の重複は先の候補を残す。手入力は食品データの候補集合に混ぜない（FR-BAL-06）。7 章で見直した同梱データを使う。
- `suggestSupplements` は `toRegisteredItems` と既存の換算・集計・判定の純粋関数を再利用し、2.2 の差分計算を行う純粋な関数。候補ごとの `analyzeBasket` の全行再集計は行わない。入出力の配列・状態を書き換えず、ID や時刻を生成しない（NFR-08）。`data` の既定値は `defaultAnalysisData`。UI からは `baseFoods` で一度作った候補集合を渡す。
- 現在の判定が `insufficient`、不足がない、候補がない場合は `[]`。候補で判定開始の品目数を水増ししない。不足のない状態で過剰だけを直す提案は IT03 の対象外。

### 2.2 追加の仮定（DES-SUG-02）

各候補を独立に 1 単位登録した状態を仮定する。実際の `register` と同じ、食品番号と表示名の一致を使う（DES-BSK-01）。既存の有効行なら個数を `min(count + 1, maximumCount)`、使い切った行なら個数 1・`usedUp = false`、なければ新しい分析用の行を 1 件加える。上限で個数が増えない候補は除く。`RegisteredItem[]` 上でこの操作を再現し、ID は不要とする。

候補を加えた後の判定は、`analyzeBasket` と同じ規則を次の差分計算で求める。量は `edibleGrams` と `unitWeights` を使う。

- 元の有効行の換算・主食以外の `NutrientTotals`（各成分の `amount`・`coveredEnergyKcal` と null の有無）・登録一致の索引を 1 回だけ求める。`referenceFor` も 1 回とし、候補間で再利用する。
- 候補ごとに実際に増える個数（`min(count + 1, maximumCount) − count`、新規・使い切った行なら 1）だけを換算し、元の合計の写しへ加算する。null 同士は null、片方にデータがあればその寄与を使う。エネルギーのデータがない行や重さ 0 以下の除外規則も `sumNutrients` と同じにする。
- 追加後の主食以外のエネルギーから `stapleItem` で主食量を求め、その寄与を加える。元の主食量を固定しない。`nutrientRatios`・`pfcRatio`・`judgeBalance` で対象 14 種を再判定し、カバー率も求める。候補評価に不要な `detailSufficiencies`、詳細画面用の値や食材名の一覧は作らない。
- 差分の補助関数は `src/core/suggestions.ts` 内に置く。現在の判定もこの準備済み合計から求め、候補関数内で別途全行を再集計しない。全行を再計算する参照計算との同値性を TC-FR-BAL-07-08 で確かめ、主食・欠損・丸めの規則を変えない。目安重量がない食品は既存どおり 100g の概算とし、結果に `approximate = true` を付ける。候補 3 件を同時に加える計算はしない。

### 2.3 評価の式と並び（DES-SUG-03）

`BalanceResult` に対する新しい純粋な関数 `lowerTargetRatio(result): number | null` を `src/core/balance.ts` に置く。

- 下限規則は既存の `sufficiency`（比。100% = 1）を返す。上限規則（塩分）は null を返す。
- PFC は `pfcPct / pfcRange[0]`（下限が正の場合）を返す。PFC の `sufficiency` は現在 null のまま。これは表示・候補評価のための下限比であり、判定の計算や保存に混ぜない。
- 不明、欠損、有限でない値、負値、PFC 下限が 0 以下の場合は null。

現在不足のキーの集合を L とする。不足量は、下限規則では `d(r) = max(0, 0.7 − lowerTargetRatio(r))`、PFC では `d(r) = max(0, 1 − lowerTargetRatio(r))`。0.7 は既存の `lowSufficiency`、PFC の 1 は目標範囲の下端を意味する。評価対象 K は下限規則と PFC の全キーとし、現在不足していないキーも含める。塩分は下限規則でないため K・L に入らない。判定できないキーの不足量は 0 と見なさず評価対象から除く。現在不明のキーが追加後に判定可能となり不足する場合は `newLowKeys` で扱う。

候補 c の評価値は `I(c) = Σ[k ∈ K、前後とも判定可能] (d(before[k]) − d(after[k]))`。既存不足の悪化と、新たに生まれる不足も減点に含める。適正だったビタミンが希釈で 70% を下回る場合や、PFC の炭水化物が下限を割る場合も、追加前の d は 0、追加後は正なので負の寄与になる。判定境界までの距離を比で比較するので、mg と g の大小や食品のエネルギー量そのものに順位を左右されない。栄養学的な重み付けの根拠はないため、全キーを同じ重みで足す（エージェントの判断、P-06）。評価値は小数第 6 位で丸め、正のものだけを残す。桁数は既存の判定の丸め方に合わせ、丸め誤差だけの提案を避けるために選んだ。

欠損による見かけの改善を避けるため、現在判定できるすべてのキーについて、追加後も判定でき、`coverage` が現在以上である候補に限る。さらに `improvedKeys` に入れるキーは、候補自身に当該成分のデータがあり、追加後の不足量が減ったものだけ。PFC の改善には P・F・C の全成分が必要。エネルギーが null または 0 以下の候補、再計算が `insufficient` の候補も除く。unknown を 0 として評価しない。

並びは次の順に比較する。

1. 新しい過剰のキーが 0 件のものを先にする。`before.status !== "high" && after.status === "high"` のキーを `newHighKeys` とする
2. 新しい不足の件数の昇順。`before.status !== "low" && after.status === "low"` のキーを `newLowKeys` とする。総不足量が減っても、別の不足を増やさない候補を優先するため、改善量とは別に比較する
3. 既存過剰の悪化件数の昇順。前後とも high のキーで、上限超過比が増えたものを `worsenedHighKeys` とする。上限超過比は塩分で `max(0, sufficiency / highSufficiency − 1)`、PFC で `max(0, pfcPct / pfcRange[1] − 1)`。前後の比を小数第 6 位に丸めて比較する。既存の塩分・脂質などの過剰をさらに増す候補を後ろにするため採用する
4. `improvement` の降順
5. `supermarketPriority` の昇順
6. 食品番号の文字列の昇順（コード単位で比較し、端末のロケールに依存させない）

最大 3 件を返す（P-06）。改善しない候補で埋めない。新しい過剰を生む候補も禁止せず、後ろに回す（FR-BAL-07）。新しい不足や既存過剰の悪化も禁止はせず順位で扱い、該当する場合はそれぞれの栄養素名と注意を画面に示す。実例の妥当性は本人の H-08 で確かめ、式を無断で調整しない。

### 2.4 ホームでの表示・登録（DES-UI-42）

`HomeScreen` の `BalancePanel` の直後、栄養詳細への入口の前に `SupplementSuggestions`（`src/ui/components/SupplementSuggestions.tsx`）を置く。見出しは「不足を補う候補」。食材名、1 単位の表示、改善する不足の栄養素、概算の注記、新しい過剰・新しい不足・既存過剰の悪化の注意を出す。候補がなければ、判定済みで不足がある場合だけ「今の条件で不足を減らせる候補がありません」と表示する。

押すと `localId("item")` を付けた既存の `register` action を dispatch し、ホームに留まる（P-02）。`registerMessage` を使って登録結果を `role="status"` で知らせる。状態変更で判定を先に更新し、候補は描画後に再計算する。候補ボタンの React の `key` は配列の添字ではなく食品番号とする。押した直後に候補ボタンをすべて無効化し、表示中の順序・枠の高さを固定する。消える候補の枠も空のプレースホルダーとして残す。フォーカスは候補欄の見出しへ移す。再計算済みでも、ポインターが候補欄から離れ、かつ候補ボタンにフォーカスがない状態になるまで新しい並びへ交換しない（キーボード操作でポインターが欄外にある場合は見出しへの移動で条件を満たす）。例えば先頭の卵を押した位置に次の候補の魚を即座に詰めず、同じ位置の連打で魚を登録しない。押下時に保持した食品番号を登録し、その後の無効化中のイベントは無視して 1 回だけ dispatch する。

候補集合の作成は静的データが変わらない限り繰り返さない。`App` の実際の判定と候補計算の状態・処理を分け、候補の仮定を実際の `analysis` や登録状態に混ぜない（FR-NUT-06）。候補計算はホームでだけ行う。判定の commit 後、2 回の `requestAnimationFrame` を経て `setTimeout` で候補計算を開始し、判定を描画する機会を先に確保する。予約・結果に状態の revision を付け、変更済みの状態に対する古い予約は中止し、古い結果は破棄する。計算待ちは「候補を計算中」とし、古い候補を操作可能なまま出さない。`data-candidates-revision` は候補が画面へ反映された時点で更新する。6 章では判定までの時間と候補までの時間を分けて記録する。

## 3. 不足の色（DES-COL）

### 3.1 割り当て（DES-COL-01）

新しい `balanceTone(result: BalanceResult): string | null` を `src/ui/balanceTone.ts` に置く。既存の `status` を先に見てから色を決める。

| 状態         | バッジの背景色                                                             |
| ------------ | -------------------------------------------------------------------------- |
| low          | `t = clamp(lowerTargetRatio(result), 0, 1)`、`rgb(255, round(255 × t), 0)` |
| high         | `#d8b4fe`（紫）                                                            |
| ok / unknown | null（不足・過剰の警告色を付けない）                                       |

不足の端点は `#ff0000`（0%）、中間は `#ff8000`（50%）、終点は `#ffff00`（100%）。RGB の緑成分だけを線形補間する。単純で再現可能、赤→橙→黄になるため採用した（中間の割り当ては P-04 が設計に委ねた判断）。整数 RGB への丸めによる段階以外は連続的に変える。PFC は下限を 100% とした比で色を決める。

下限規則では 70% 未満だけが不足なので、PFC 以外の不足色は赤〜約 `#ffb300` の橙までしか出ず、黄色にはならない。関数の色尺度の終点を 100% とする決定と、適正に色を付けない E-49 は両立する。PFC の不足は下限に近づくほど黄に近づく。不足なのに比が得られない異常な入力は色を付けず、文字を残す。

### 3.2 読みやすさ（DES-COL-02、DES-UI-01 の変更）

色を文字自体に使わず、黒 `#000000` の「不足」「過剰」を塗った背景の上に置く。食品名・栄養素名などは通常の本文色を維持する。色コードは外部データではなくエージェントの配色案。**コントラスト比は本 Issue では未計算で、実装で確かめる**。採用条件は通常文字の比 4.5:1 以上とし、実装 Issue で使用するアクセシビリティ基準の一次資料・計算式を記録して、赤〜黄の全 256 通りと紫を検査する。4.5:1 はこの設計の検査目標であり、ここで規格適合を確認したという意味ではない。

既存 CSS の low / high の文字色・背景色の上書きを確認し、ホームと栄養詳細で同じ `balanceTone` を使う。警告色を使う対象はバッジだけに限る。ok / unknown のバッジはどちらも中立の灰色背景 `#f3f4f6` と黒文字にし、既存の適正の緑は除く。栄養詳細の `.detail-fill`（ok・info を含む棒）と `.detail-value`（PFC の値の目印）は全状態で中立の灰色 `#6b7280` に統一し、low / high / ok による色の上書きを除く。PFC の目標範囲の帯 `.detail-band` と棒の地は薄い灰色 `#e5e7eb` とし、緑の適正表現を残さない。値の本文色、棒の長さ・目盛り・範囲・目印の位置は維持し、判定しない栄養素も警告色にしない。バッジだけで状態を色と文字で示し、棒は量と範囲を示す役割に分ける（E-49）。色なし・強制カラーでも「不足」「過剰」の文字と栄養素名が読める構造を保ち、判定できない説明・データの欠けの注記は維持する（NFR-07）。

## 4. 手入力を覚える・下書き（DES-MAN）

### 4.1 状態と再登録（DES-MAN-01）

`AppState.manualFoods` を「登録から参照する食品かつ覚えた食品の台帳」として使い、同じ成分値を別配列に二重保存しない。DES-BSK-04 の削除時の食品削除と、DES-STO-05 の未参照食品の破棄をやめる。すべての新しい手入力は覚える。再登録は既存の `register` action を使い、`foodId` に同じ `manual-` ID、`displayName` に覚えた名前を渡す。既存の行への加算・使い切った行の再利用は DES-BSK-01 のまま。

同じ名前で新しく入力した食品は既存どおり別 ID とする（DES-BSK-08）。名前だけで成分の違う食品を上書きしない。表示は棚と「手入力」を添え、同名・同棚が複数あれば保存順の番号を付けて区別する。編集・削除・自動的な件数制限は IT03 では設けない。登録していない覚えた食品は `toRegisteredItems` に混ぜず、集計されない。

### 4.2 登録画面（DES-UI-43、DES-UI-35 の変更）

- 簡易・詳細の両モードで「覚えた食材」の区画を通常食品の一覧の後、手入力フォームの前に別区画として表示する。検索時も通常食品の検索結果の後に別区画で表示し、通常の結果に混ぜない。棚と `normalizeSearchText` による名前検索を同じ条件で使う。`手入力 / <棚>` の棚を解釈する `manualFoodShelf(food): FoodShelf | null` を `core/manualFoods.ts` に新設する。選択肢は `registrableShelves` のまま。完全に `手入力 / <棚>` と一致し、棚が選択肢に含まれる場合だけその棚を返す。未対応の棚・形式違い・空文字は null とし、UI では「その他」に対応付ける。
- 未検索時は覚えた順（新しいものから）を保つ。通常食品の「よくある」順を変えず、上限のない覚えた一覧が FR-ING-04 の優先表示を押し下げないよう、通常一覧の後に置く。覚えた食材は通常食品の 80 件制限の外にすべて出し、2 回目の登録に開閉操作を要求しない。増えたときの影響は性能計測で確認する。
- 覚えた食材を 1 回押すと再登録し、登録画面に留まって知らせる。ホームから登録タブ→覚えた食材の 2 タップで完了する（H-09、NFR-02）。
- 検索結果が通常・覚えた食材とも 0 件なら「この名前で手入力」を出す。押した時点の `query.trim()` を `ManualFoodForm.name` に入れてフォームへフォーカスを移す。既にフォームを編集している場合は自動上書きせず、押す操作によって名前だけを置き換える。検索語の変更だけでは入力値を変えない。
- 名前・棚・登録ボタンは常に表示。成分の欄は初期状態で閉じた `<details>` とし、`<summary>` は「成分を入力・似た食品から下書き（任意）」。閉じても入力内容を消さない。登録成功・入力クリアでフォームと開閉状態を初期化する。未入力成分は既存の `parseManualValue` で null、エネルギーなしの説明は常時出す。

### 4.3 似た食品からの下書き（DES-MAN-02、DES-UI-44）

成分欄の中に「似た食品を探す」検索と選択肢を置く。食品データの `baseFoods` を検索し、正式名称・食品番号を示して利用者が選ぶ。下書きの検索は登録とは用途が異なるため、主食を含む同梱食品を検索できる。アプリによる自動選択や生成はしない。

`manualDraftFrom(food: FoodItem)`（`src/core/manualFoods.ts`）は `nutrientsPer100g` の写しと `sourceFoodId` を返す。UI は成分値をフォームの文字列に変換し、null を空欄にする。名前・棚は変更しない。選択操作は「この食品の成分で下書きを置き換える」と明示し、既にある全成分欄を置換する。成分は `nutrientDefinitions` の全項目を編集できるようにし、`basicNutrientDefinitions` だけで見えない値を保存しない。

```ts
// src/core/manualFoods.ts。FoodItem 自体や同梱の食品データは変更しない。
type ManualFood = FoodItem & { sourceFoodId?: string };
```

`AppState.manualFoods` と `addManualFood.food` を `ManualFood` に拡張する。写した食品の番号を保存し、フォームと覚えた食材に「下書き元: <正式名称>（食品番号 …）。登録値は手入力」と表示する。変更後も下書き元を残すが、原典と同じ値だとは表示しない。データ更新で番号が見つからなくなったら「下書き元: 食品番号 …（現在の食品データにはありません）」とする。これは来歴であって外部キーではないため、手入力食品や登録行を削除する理由にしない。

保存するのは利用者が確定した成分値。`refusePct` は従来どおり null とし、下書き元の廃棄率・ID・分類はコピーしない。計算は既存の表示名に対する目安重量、なければ 100g 概算を使う。`foods.json` を変更せず（CST-01）、実在の値だけを利用者が明示選択して写す（CST-04）。入力をクリアすると来歴も消す。

### 5.1 保存の版 2（DES-STO-08）

`storageVersion = 2`。`serializeState` は `{ version: 2, items, manualFoods, profile }` だけを書き、`manualFoods` に全台帳と任意の `sourceFoodId` を含める。台帳の意味と形を変えるため P-08 に従って版を上げる。取り消し用の一時状態は保存しない。

- DES-STO-05 は未参照の食品を残す点だけを変える。覚えた食品の既存の形の検査を再利用する。空の名前、解釈できない棚の旧データは現在の読み込み互換を維持し、登録画面では「その他」として表示する。成分を勝手に埋めない。

### 5.2 退避できなければ保存しない（DES-STO-09）

`src/ui/storage.ts` の現行 `loadAppState` は、読めない原文を `backupKey` に退避できた場合だけ `available = true` にする。`openBrowserStore` の書き込み不可、読み込み不可、退避の例外の場合は false。`App` は `loaded.available` が false の間、`saveAppState` を呼ばない。状態の編集はメモリ上で続け、`StorageNotice` で保存・退避できなかったことを知らせる。再読み込みまで自動で保存を再開しない。

これは現在実装済みの規則の文書化（IT03-PLAN 3.2）。元の `weekmeal:state` を初期状態で上書きしない。`backedUp` は実際に退避したときだけ true。単体テストに加え、TC-NFR-12-33 を、起動後に登録しても原文が残るところまで強化する。

### 5.3 直前の削除の取り消し（DES-BSK-09、DES-UI-45）

```ts
// src/core/basketSession.ts（純粋関数）。保存対象の AppState は変更しない。
type PendingRemoval = { entry: BasketEntry; index: number };
type BasketSessionState = {
  appState: AppState;
  pendingRemoval: PendingRemoval | null;
};
type BasketSessionAction = BasketAction | { type: "undoRemove" };
// basketSessionReducer(state, action): BasketSessionState を新設する。
```

`App` は `BasketSessionState` を `useReducer` で持つ。通常操作は既存の `basketReducer` に `session.appState` を渡し、削除・復元と取り消し対象の保持・破棄をセッション reducer が管理する。保存・分析・候補には `session.appState` だけを渡す。`replace` と初期化・再読み込みでは読み込んだ `AppState` を包み、一時状態は null にする。既存の `BasketAction`・保存型・既存 reducer のテストに一時状態を必須化しない。

- `remove` は対象行と `session.appState.items` の添字を記録し、その行だけを消す。覚えた食品は DES-MAN-01 に従い残す。知らない ID の削除は状態と既存の取り消し対象を変えない（DES-BSK-06）。
- `undoRemove` は保存した添字に、同じ ID・食品・表示名・個数・`usedUp` の行を戻して `pendingRemoval` を null にする。全体の状態を過去に巻き戻さない。空の場合は状態を変えない。
- 次の有効な `register` / `addManualFood` / `increment` / `decrement` / `toggleUsedUp` / `remove` は、以前の取り消し対象を消す。新しい `remove` は新しい 1 件に置換する。設定の変更と画面移動は消さない。`replace` は取り消し情報を引き継がない。ここで有効とは登録・個数・使い切ったの状態が実際に変わる操作とする。無効 ID や上限・下限で変わらない操作では消さない。
- これにより復元位置に影響する食材操作と同じ ID の再登録の衝突を避ける。時間による期限は設けない（操作機会を奪わず、純粋な reducer を保つため）。再読み込みで対象は消える。1 回戻した後の 2 回目は何もしない。
- ホームの一覧の直前に「<食材名>を削除しました」「元に戻す」の通知を置く。削除の確認ダイアログは挟まない。通知文は `role="status"`、ボタンは独立してキーボード操作可能にする。削除後は「元に戻す」へ、戻した後は復元行の操作へフォーカスを移す。使い切った行は既存の表示上の並べ替えを維持し、その区画内で元の位置に戻す。

### 6.1 時間の測り方（DES-PER-01）

本番ビルドの `vite preview` に対する専用 `e2e/performance.spec.ts` を作る。`performance.now()` とイベントの capture、判定領域の DOM 更新を監視する `MutationObserver` を E2E から注入する。始点は対象ボタンの click イベントを受けた時点、終点は対応する変更後の**判定結果の更新**が commit され、その後の連続する 2 回目の `requestAnimationFrame` を迎えた時点とする。1 回目は描画前に呼ばれるため、間に描画機会を 1 回含む保守的な上限として測る。NFR-03 の終点は SRS の文言どおり判定であり、候補の完了は含めない。前景のタブで行い、非表示状態では測らない。Playwright のクリック待ちや Node 側の通信時間を計測に含めない。

判定の文言が変わらない入力でも完了を識別できるよう、`App` の main 要素に `data-analysis-revision` を設ける。UI で食材操作の dispatch ごとに増やす番号を付け、その番号に対応する判定が計算され画面に commit されたときに更新する。テストは操作前の番号から変わることを待つ。core に時計や DOM を入れない。通常の登録画面での登録と、ホームの候補登録をそれぞれ測る。登録画面は判定結果を表示しない既存仕様なので、`App` の判定計算を反映した commit 後の 2 回目の描画コールバックを終点にし、その解釈を計測記録に明記する。ホームでは実際の判定 DOM 更新まで確認する。登録画面を開く時間の回帰も別途記録する（E-47）。

計測用データは食品番号と個数を固定し、3 品目（判定開始）、30 行（通常を想定した設計上の試料）、100 行（負荷試料）を保存データで用意する。各操作を準備済みの同じ状態から 5 回ずつ行い、全測定値と最大値を添付する。試料数と回数はエージェントが回帰検出用に選んだもので、実利用件数の調査値ではない。候補集合は実データ全体を使い、覚えた食品も負荷試料に含める。判定の内容の正しさは通常の E2E で別に確認する。

性能の見積もりと予算は次のとおり（外部の測定値ではなくレビューでの観測と設計目標）。

- レビューでは候補 80 件・登録 100 行の全行再計算が 12 コアのデスクトップの Node で約 30 ms、4 倍 slowdown 相当で約 120 ms と見積もられた。ブラウザや実機での達成確認ではないが、候補を判定更新の前に計算する方式は 100 ms を使い切るおそれがある。
- 2.2 の差分計算では、行数 N・候補数 C・成分数 M に対する集計を `O(C × N × M)` から `O(N × M + C × M)` に減らし、栄養詳細の計算も省く。N=100、C=80 なら成分ごとの行処理の規模は約 8,000 から約 180 になる。ただしこの比を実行時間の短縮率とは見なさない。
- 候補集合の初期生成を別計測し、定常時の差分準備と候補全件の計算は、100 行・80 件・4 倍 slowdown の専用条件で **50 ms 以内**を設計上の予算とする。判定描画後から候補の revision の commit まで（待機・描画を含む）は **100 ms 以内**を目安とする。候補の反映時間の計測はポインター・フォーカスが候補欄外の条件で行い、2.4 の連打防止による意図的な表示待ちは別記する。どちらも NFR-03 とは別の診断値であり、超過時は I で処理の内訳を調べて対策をレビューする。達成済みとは扱わない。
- 差分計算だけでは描画との競合を避けられず、遅延だけでは長い処理が残るため、差分計算と判定描画後の実行の両方を採用する。`data-candidates-revision` で候補までの時間も別に記録し、古い結果を表示しないことは機能 E2E で失敗条件とする。

性能 E2E は専用 Playwright project `performance`（Chromium・360×740、mobile と同じ操作設定、`testMatch: /performance\.spec\.ts/`、`fullyParallel: false`）に分け、既存 mobile / desktop は同ファイルを `testIgnore` する。`test.describe.configure` による部分的な直列化は採らない。他プロジェクトとの同時実行も避けるため、CI の通常 E2E は `--project=mobile --project=desktop`、その終了後に別の呼び出し `--project=performance --workers=1` で実行する。実装 Issue I で設定・CI を更新する。

CPU 制限なしと 4 倍の CPU slowdown を別々に測る。CI では時間の 100 ms 超過や候補予算の超過は**記録のみ**とし、環境変動による時間超過で自動マージを止めない。一方、revision の未更新・候補の不整合・例外・計測不能は通常の E2E タイムアウト等で**失敗**にする。計測の生値・最大値・予算との差を artifact に必ず残し、時間の assert だけを CI で無効にする。

4 倍は比較用の設計上の試験条件であり、「中位のスマートフォン相当」を確認した値ではない。CI の機器・OS・ブラウザ版・制限・試料・コミットを記録し、CI の成績だけで SRS の実機相当条件の達成とは断定しない。反復末に本人の端末またはレビュアーと合意した中位相当の端末で同じ測定を行い、NFR-03 は各操作・各試料の全 5 回が 100 ms 以内なら合格、1 回でも超えたら不合格とする。端末・条件が決まらなければ NFR-03 の達成は未確認として報告する（10 章）。

### 6.2 axe と操作（DES-E2E-07, 08）

axe は `critical`・`serious` の違反が 0 件であることを必須にし、ほかの違反と判定保留も添付して査閲する。この区分を「重大」の検査上の扱いとして選ぶ（エージェントの判断）。規則の一括除外はしない。候補あり、取り消し通知あり、成分欄を開いて下書きを選んだ状態、食品詳細を開いた状態でも実行する。mobile / desktop の既存 2 プロジェクトと CI の `npm run test:e2e` に含める。現在は依存にないため導入は実装 Issue で行う。

axe だけで全操作を確認したことにはしない。候補・取り消し・折りたたみ・再登録・下書きは Tab / Enter / Space とフォーカスで確認する。DES-E2E-05 の対象に新しいボタン・summary を加え、360px の横スクロールなしと 44px の操作領域を保つ。IF-02 の全機能の実演範囲の確認は計画書 8 章の本人確認事項のままとする。
