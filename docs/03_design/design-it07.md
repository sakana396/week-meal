## 1. 範囲と既存設計との関係

本人の実際の買い物で、貼り付けの効果と炭水化物の不足判定を確かめる。製品コード、判定規則、目安重量、主食の比率、PFC 計算方法、表示、保存形式は変えない。本人はデータの確認を後回しにしているため（E-130）、手順の設計と記録の準備を先に行い、入力を受け取るまで実地検証・再計算を未実施とする。

| 既存の設計 | IT07 で行うこと |
| --- | --- |
| DES-CAT-07、DES-RCP-02〜07 | 方式を維持し、実地検証の記録と判定方法を DES-RCP-08 に定める |
| DES-QTY-02、DES-NUT-01〜04、DES-ANL-01・03、DES-BAL-02〜05 | 方式を維持し、実際の入力から結果を辿る調査方法を DES-BAL-07 に定める |
| DES-IT06 4 章 | 固定例による調査記録を当時の記録として残し、今回の本人のデータによる再調査から参照する |

採番前に既存文書を検索し、RCP の最大が 07、BAL の最大が 06 であることを確認した。新しい設計 ID は調査・検証の手順を指し、製品の新しい関数や機能を意味しない。

## 2. 入力と記録の共通ルール

本人が会話で示した範囲のデータを使い、アプリの保存データを自動送信する機能は作らない。各記録には確認日、対象の買い物、公開 URL と確認できた配信の版、再計算に使ったコードのコミットを記載する。公開版と再計算の版が異なるときは差を確認し、同じ実行結果として扱わない。

入力の表は次の列を基本とし、不明な値を推測で埋めない。

| 列 | 内容 |
| --- | --- |
| 元の入力 | 貼った行の名前と量・単位。手入力の場合はその旨 |
| 当初の当てはめ | 確認の一覧での食材名、量、登録する側か「登録しない物」か |
| 本人の修正 | 名前・食品の選び直し、量・単位、チェックの変更。変更なしも記録 |
| 最終の登録 | 実際に登録した名前、量・単位。分かる場合は食品番号と手入力の成分値 |
| 買った量・根拠 | 本人が確認した内容。目安・概算と実測を区別する |

元の入力、確認中の修正、登録後の修正を別々に記録する。検証結果に必要のない店名・金額などを求めない。記録をリポジトリで公開する場合、本人が共有した内容のうち検証に必要な項目を抜粋し、元データ全体の転載を前提にしない。

## 3. レシート貼り付けの実地検証（DES-RCP-08）

### 3.1 公開版と操作

GitHub の配信 run と対象コミット、配信先 URL を確認し、確認できなければ未確認と書く。確認する公開版は IT06 の分けた食材名と言い換えの表を含むものとし、配信 run の成功と実際に開いた画面での操作結果を区別する。

本人の買い物データが得られたら、対象の買い物と主食設定を確かめ、指示文のコピー、元テキストの貼り付け、確認の一覧、登録後の一覧を順に記録する。確認のために作業用のブラウザで再現した場合は、本人が実際に使った結果とは別欄に書く。

### 3.2 仮説の結果

- H-17: 言い換えに該当した名前、元の表記表示、「登録しない物」と名前を直した物の件数を記録する。対象の表記がなければ未検証。対象があっても修正を要した場合、その内容を示し、成功と決め付けない。
- H-18: ミニトマト・かいわれだいこんの購入があった場合、当初の登録名・量、本人の修正後の量、買った量とのずれについての感想を記録する。対象を購入していなければ未検証。概算重量の承認（E-122）を実測の証拠にしない。
- 件数は行単位を基本とし、同じ行を名前と量の両方で修正した場合は「修正した行 1 件」とし、修正内容を併記する。「登録しない物」は当初表示された行数と、本人が最終的に除外した行数を区別する。

不一致は改善候補として記録する。名前の表や量の換算を、この Issue の中で変更しない。仮説の評価は本人に感想を聞いたうえで、確認できた範囲に限定して記す。

## 4. 炭水化物の不足判定の再調査（DES-BAL-07）

### 4.1 再現に必要な入力

買い物の全行の食材名・量・単位、当時の主食の種類・盛り、性別・年齢区分の設定を確認する。登録時の表示名と食品番号が分かれば両方を使い、旧い「トマト」などの名前を現在の名前へ自動で置き換えない。手入力の食材は栄養成分値も必要になる。不明な場合は該当行を示し、本人に確認するまで正確な再現を完了扱いにしない。

通常の主食設定（E-119）を、その買い物の当時の設定と決め付けない。設定が不明なら、仮定を明示した参考計算はできるが、本人の判定を再現したとはしない。実際に食べる主食の量は分かる範囲で確認し、回数だけから主食のエネルギー比率を計算しない。

### 4.2 再計算と照合

1. 登録行を既存の `RegisteredItem` に対応させ、使用した入力を表に残す。重さの入力は買うときの重さとして既存の `edibleGrams` で換算する。
2. `analyzeBasket` で当時の設定の結果を求める。`insufficient`、`unknown`、データの欠け、概算の行を確認し、判定できない結果を不足と呼ばない。
3. 既存の `sumNutrients`・`stapleItem`・`nutrientRatios`・`pfcRatio` で中間値を記録する。主食を除く合計、設定に応じた主食の追加量、追加後の合計、PFC 比、判定で使う範囲を記す。
4. 同じ買い物のまま主食なし・各盛りの設定を比較する。比較のために変えた設定は本人の当時の設定と分けて記す。
5. 手計算または別の単純な計算で、主食の追加量と PFC 比を照合する。丸め前の値、判定前に小数第 6 位で丸めた値（DES-BAL-04）、表示用の値を区別し、表示値だけから境界の判定を決めない。

実行には、一時的な Vitest の調査用ファイルなど既存の TypeScript 実行基盤を使える。再実行できる入力と計算手順・コマンドは調査記録に残し、一時ファイルを削除したことだけで手順を失わないようにする。調査用のファイルは製品コードの変更と混同せず、永続的な自動テストの追加が必要ならテスト仕様書と対応を更新する。

### 4.3 原資料との比較と結論

成分列や別の PFC 計算方法を比較する必要があれば、成分表などの原資料を調べ、版・箇所と参照先を比較値の近くに記す。資料を確かめられなければ未検証と書く。既存の `CHOCDF-` や 4・9・4 の選択を、調査のために製品側で変更しない。

原因を特定できたか、再現できただけか、資料・入力の不足が残るかを分ける。入力の修正で結果が変わった場合も、製品の不具合と直ちに断定しない。本人には結果、調査の限界、対応案を報告し、直し方を選ぶ前に結果を見てもらう（E-128）。今回は修正しない。

## 6. 試験の方針

[TST-IT07](../04_test/test-spec-it07.md) に手動検証・調査の確認項目を定める。入力が未受領のため具体的な栄養値を期待値として作らず、実際の入力が揃ったときに既存設計と独立した照合計算を根拠に値を記録する。製品の単体・E2E の既存の期待値は変えない。

製品コードの追加は予定しない。実地検証で不具合を見つけても、今回の Issue は記録と報告までにし、修正は本人の判断と別の計画・Issue による。

## 9. レビューで確かめる点・計画・要求への提案

- 元の入力と修正後の量、公開確認と本人の実地検証、通常設定と当時の設定を分けて記録する方式。
- 本人のデータがない項目は未実施とし、対象を試せない仮説は未検証とする方式。
- 一時的な調査用ファイルを使っても、再実行に必要な入力・手順は調査記録へ残す方式。
- 設計 ID は検証・調査の手順の識別に限り、既存の製品設計を置き換えない。
- 計画・要求への提案はなし。具体的な記録方法はエージェントの設計判断であり、本人が文を確認したことにはしない。
