## 1. 範囲と既存設計との関係

IT05 は、登録行の量を個数か重さで表せるようにし、外部の AI で作ったテキストを貼って一括で登録できるようにする。判定の規則（14 種、70% / 130%、主食の足し方）、目安重量のデータ、色、候補の評価式は変えない。`src/core/` は時刻・DOM・保存先・ネットワークに依存しない（NFR-08）。

| 旧設計 | IT05 の置き換え・継続 |
| --- | --- |
| DES-QTY-02（個数 × 購入時の重さ × (1 − 廃棄率)） | 個数の行は継続。重さの行は DES-QTY-04 で「買うときの重さ × (1 − 廃棄率)」とする |
| DES-SHP-01 の `BasketEntry.count` | `quantity`（個数か重さ）に置き換える。DES-QTY-03 |
| DES-SHP-02 の `register`・`increment`・`decrement` | 1 回押しの登録は継続（新しい行は 1 個）。増減は個数の行だけ。重さの行への 1 回押しは DES-QTY-06。量の直接の指定 `setQuantity` と一括登録 `registerMany` を足す |
| DES-SHP-03、`RegisteredItem.count` | `quantity` を渡し、換算を DES-QTY-04 に寄せる。判定以降は継続 |
| DES-SUG-02〜04 | 候補は「1 単位を足す」まま。既存の行が重さなら、その重さに 1 単位の買うときの重さを足して評価する（DES-QTY-06） |
| DES-STO-10〜12、ADR-0004 | 版 4 に上げる。DES-STO-13、14 |
| DES-UI-20, 21（行の表示・増減） | 行に「個・g・kg」の切り替え、重さの入力、目安の重さを加える。DES-UI-49 |
| DES-PER-03 | 日付の変更の高速化（DES-PER-05）と、新しい操作の計測を足す |

## 2. 量の表し方

### 2.1 量の形（DES-QTY-03）

```ts
type Quantity =
  | { kind: "count"; count: number } // 0.5 刻み、0.5〜999（DES-SHP-02 と同じ）
  | { kind: "weight"; grams: number; unit: "g" | "kg" }; // 買うときの重さ
type BasketEntry = { id: string; foodId: string; displayName: string; quantity: Quantity };
```

- `grams` は常に g で持つ。`unit` は入力と表示の単位で、計算には使わない。kg の入力 2.5 は `grams: 2500, unit: "kg"` として持つ
- 重さの範囲は 1 g〜100,000 g（100 kg）。g の入力は整数、kg の入力は 0.1 kg 刻み（100 g 刻み）とする。範囲外・非有限・0 以下は受け付けない（エージェントの判断。10 kg の玉ねぎ（E-89）と 2 kg の鶏肉（E-90）を収める）
- 新しい行は今どおり `{ kind: "count", count: 1 }` で入る（FR-ING-01、FR-QTY-01）

### 2.2 可食部への換算（DES-QTY-04）

`edibleGrams(food, unitWeight, quantity)` に改める。

- 個数: 既存の DES-QTY-02 のまま。目安重量がなければ 1 単位 100 g の概算（FR-QTY-05）
- 重さ: `grams × (1 − 廃棄率 ÷ 100)`。廃棄率は目安重量の上書き → 代表食品の成分表の値 → 0 の順（DES-QTY-02 と同じ）。目安重量の有無にかかわらず、重さは利用者が入れた値なので**概算にしない**（`approximate: false`）
- 手入力の食材（DES-MAN）は廃棄率を持たないので 0 とする。入れた重さをそのまま可食部とする
- 0 以下・非有限は 0 g（既存の規則）

`analyzeBasket` の 3 品目の判定（DES-ANL-03）と感度分析（`factor` 倍）は、`quantity` の量（個数または g）に掛ける。

### 2.3 切り替え（DES-QTY-05、P-08）

行で「個・g・kg」を切り替えるとき、量を次のように引き継ぐ。純粋な関数 `convertQuantity(quantity, to, unitWeight)` にする。

| 元 → 先 | 換算 |
| --- | --- |
| 個 → g・kg | `count × 1 単位の買うときの重さ`（目安重量がなければ 100 g）。kg は 100 g 単位に丸める |
| g ⇄ kg | `grams` を保ち、`unit` だけ変える。kg に変えるときは 100 g 単位に丸め、最低 100 g |
| g・kg → 個 | `grams ÷ 1 単位の買うときの重さ` を 0.5 刻みに丸め、0.5〜999 に収める |

換算の結果は目安なので、切り替えた直後に入力欄へ焦点を移し、利用者が直せるようにする。

### 2.4 目安の重さの表示（DES-QTY-07）

個数の行には「1 パック ≒ 250 g」の形で、`unitWeights` の `purchaseG`（買うときの重さ、廃棄部分を含む）を示す（FR-QTY-08）。単位は `unitWeights` の `unit`。目安重量がない食材と手入力の食材は「1 単位 ≒ 100 g（概算）」と示す。重さの行には示さない。

### 2.5 登録と増減（DES-QTY-06）

- 1 回押しの登録で、同じ食材の行がすでにあるとき: 個数の行は今どおり +1。重さの行は「1 単位の買うときの重さ」（なければ 100 g）を `grams` に足す。上限を超えるときは変えない
- 増減ボタン（±0.5）は個数の行だけに出す。重さの行は数値の入力で変える
- `setQuantity(shoppingId, id, quantity)` を reducer に足す。範囲外は何もしない。食材 1 行の削除の取り消し（DES-SHP-02）は `quantity` ごと戻す
- 補う候補（DES-SUG-02）は 1 単位を足した場合を評価する。既存の行が重さなら、その `grams` に 1 単位の買うときの重さを足して評価し、候補を押したときも DES-QTY-06 の 1 回押しと同じ結果にする

## 3. 保存の版 4（DES-STO-13, 14、ADR-0004 の追記）

### 3.1 形式・移行（DES-STO-13）

形式は `{version:4, shoppings, manualFoods, profile}`。行は `{id, foodId, displayName, quantity}`。`migrations[3]` は各行の `count` を `{kind:"count", count}` に置き換える。版 1〜3 は既存の移行を順に通る。移行は値を変えないので、移行でデータは失われない。

退避（REV-043 #C の対応）: 版の移行の前の原文は、版ごとのキー `weekmeal:state:backup-v<元の版>`（例: `backup-v3`）に退避し、**そのキーがまだないときだけ**書く。一部の破棄（不正な行・不正な買い物を捨てたとき）の原文は、今どおり `weekmeal:state:backup-migration` に書く。これで、版 2 や版 3 の原文が、後の一部の破棄で上書きされない。退避に失敗したら、その起動中の自動保存を止める（DES-STO-10 と同じ）。

### 3.2 検査と通知（DES-STO-14）

- `quantity` の検査: `kind` が `count` なら DES-STO-11 の個数の規則、`weight` なら `grams` が 1〜100,000 の有限数、`unit` が `g` か `kg`。余計なキーは持ち込まない。不正な行は捨てて件数を知らせる（既存）
- 空の不正な買い物（行のない、日付や ID が不正な買い物）は、捨てた買い物の件数に数えるが、捨てた**行**の件数には数えない。知らせる文は「買い物 N 件・食材 M 件を読み込めませんでした」のように分けて書く（REV-043 #D の対応）
- 一部の破棄の退避に失敗して保存を止めたときは、「読み込めなかったデータを退避できなかったので、保存を止めています。ブラウザの保存領域を確かめてください」のように理由を示す（REV-043 #B の対応）
- 同じ食材の加算（DES-SHP-02 の `register`）では、行 ID の全体の重複を調べない。新しい行を作るときだけ調べる（REV-043 #E の対応）

## 4. レシートの貼り付け（DES-RCP-01〜05、ADR-0006）

### 4.1 画面と遷移（DES-RCP-01）

- 登録画面（`#/register?shopping=<id>`）に「レシートから登録」を置き、`#/receipt?shopping=<id>` に移る。登録先は登録画面と同じ規則（DES-SHP-01、DES-UI-46）で、ホームからなら最新の買い物、履歴の詳細からならその買い物（FR-RCP-01、E-97）
- 買い物が 1 つもないときは、ID なしの `#/receipt` とし、一括登録のときに今日の日付の買い物を作る（DES-SHP-02 の初回登録と同じ。SRS が設計書に委ねた点）
- 画面は 3 段: (1) 指示文とコピーボタン、(2) 貼り付け欄と「読み取る」ボタン、(3) 確認の一覧と「N 件を登録」ボタン
- 貼り付けたテキストは画面の状態だけに持ち、保存しない。外部に送らない（NFR-14）。画面を離れると消える

### 4.2 指示文（DES-RCP-02）

純粋な関数 `receiptPrompt(names: string[]): string` で作る。`names` は登録の一覧の食材名（登録できる棚の代表の表示名、`registrableShelves`）と、覚えた手入力の食材名（DES-MAN）を、重複を除いて五十音順に並べたもの。指示文には次を書く（文面は実装 Issue で固める）。

1. 添付するレシートの画像から、**食べ物だけ**を書き出すこと。食べ物でない物と、下の一覧にない物は書かないこと（E-98）
2. 食材名は、下の一覧の名前のどれか 1 つをそのまま使うこと
3. 1 行に 1 品、`食材名,量` の形で書くこと。量は、重さが分かれば `300g` や `2kg`、分からなければ個数（`2`）。量が分からなければ `1`
4. 説明や見出しは書かないこと
5. 食材名の一覧（1 行に 1 つ）

コピーは `navigator.clipboard.writeText` を使う。使えないときは、指示文を読み取り専用の欄に全部選んだ状態で見せ、「長押ししてコピーしてください」と示す。一覧が約 250 件なので、指示文は数千文字になる。実装 Issue で実際の文字数を記録する。

### 4.3 読み取り（DES-RCP-03）

純粋な関数 `parseReceiptText(text, catalog)` で、行ごとに次の順で読む。例外は投げず、読めない行は「一覧にない物」として返す。

1. Unicode の NFKC で正規化する（全角の数字・英字・コンマを半角にする）
2. 空行、`` ``` `` の行、見出しらしい行（`#` で始まる行）を飛ばす。行頭の `- `、`・`、`* `、`1.` などの箇条の印を外す
3. 最後のコンマ（`,`、`、`）かタブで、名前と量に分ける。区切りがなければ、最後の空白のあとが量の形なら量とし、そうでなければ全体を名前とする
4. 量の形は `数値` / `数値 g` / `数値 kg`（大小文字を問わない）。`個`・`本`・`パック` などの単位の言葉は外して個数として読む。量がない・読めないときは個数 1 とし、確認の一覧で「量を確かめてください」と印を付ける
5. 名前を `normalizeSearchText`（DES-UI の検索と同じ正規化）で比べ、登録の一覧の食材名か手入力の食材名と**完全一致**するものだけを当てる。あいまい一致はしない（指示文で一覧の名前を使うよう頼んでいるため。ADR-0006）
6. 当たらない行は「一覧にない物」として、元の文字列を返す

返り値は `{ candidates: { line, displayName, foodId, quantity, needsCheck }[], unmatched: { line, text }[] }`。同じ食材が複数の行にあっても、この段階ではまとめない。

### 4.4 確認の一覧（DES-RCP-04）

- 当たった行ごとに、登録するかのチェック（初期は全部オン）、食材名、量の欄（DES-UI-49 と同じ「個・g・kg」と入力）を並べる。食材名は変えられない。違う食材なら、チェックを外して登録画面で登録する
- 一覧にない物は「登録しない物 N 件」の見出しの下に、元の文字列を並べる（FR-RCP-03、E-98）。登録はしない
- 「N 件を登録」はチェックした行の数を示す。0 件なら押せない
- 量の欄が不正なら、その行に理由を示し、登録ボタンを押せなくする

### 4.5 一括登録（DES-RCP-05）

reducer に `registerMany(shoppingId, entries, initialShopping?)` を足し、1 回の dispatch で原子的に登録する。各行は次のように扱う。

- 同じ買い物に同じ食材（食品番号と表示名）の行があるとき: 量を足す。種類が同じならそのまま足し、違うときは貼った側を既存の行の種類へ DES-QTY-05 で換算して足す（P-07）。上限を超えるときは上限で止め、確認の結果に「上限で止めた」と書く
- ないとき: 新しい行を、貼った量で作る（FR-QTY-01 の例外。FR-RCP-01）
- 貼ったテキストの中で同じ食材が複数あるときも、同じ規則で順に足す

登録後は登録先の画面（最新ならホーム、前の買い物なら履歴の詳細）に移り、「レシートから N 件を登録しました（登録しない物 M 件）」を `role="status"` で示す。一括登録の取り消しは作らない（確認の一覧で確かめてから登録するため）。

## 5. 行の表示（DES-UI-49）

- 行に量の種類の切り替え（「個」「g」「kg」の 3 つのボタンか、ラジオのまとまり）を置く。今の種類を `aria-pressed` か `checked` で示す
- 個数の行: 今の増減ボタンと個数、その下に目安の重さ（DES-QTY-07）
- 重さの行: 数値の入力欄（`inputmode="decimal"`）と単位。確定（Enter・焦点を外す）で `setQuantity` を dispatch する。不正な値は欄の下に理由を示し、状態を変えない
- タッチの対象は 44 px 以上（NFR-07 と既存の行に合わせる）。axe の検査に足す（NFR-06）

## 6. 性能（DES-PER-05, 06）

### 6.1 日付の変更の高速化（DES-PER-05）

IT04 の計測では、CPU 4 倍で 100 行の買い物の日付を変え、最新が入れ替わるときに最大 123.3 ms だった（IT04-RETRO 2 章）。実装 Issue では、まず Chrome の Performance パネルか `performance.measure` で、この操作の内訳（reducer、分析、描画、保存、候補）を測って記録し、主な原因に対して次を順に試す（エージェントの判断）。

1. 買い物ごとの分析を、画面側で覚える。`analyzeShopping` は純粋なので、`Shopping.items` の配列・`manualFoods`・`profile` の参照の組をキーに `WeakMap` で結果を覚える。日付の変更は `items` の参照を変えない（DES-SHP-02）ので、詳細画面で求めた分析をホームでそのまま使える
2. 今は描画のたびに求めている詳細画面の分析（`selectedAnalysis`）を、1 の覚えた結果から引く
3. 保存（`JSON.stringify` と `localStorage`）が主な原因なら、描画の後へ遅らせる（判定の更新の 100 ms には含めない）

判定の規則と表示は変えない。速くした後も、TC-NFR-03-04 の全条件の結果が変わらないことを確かめる。

### 6.2 計測（DES-PER-06）

DES-PER-03 の計測に、重さの入力・量の種類の切り替え・貼り付けの一括登録（30 件）を足すかは実装 Issue で決める。足すなら同じ方法（クリック受信から判定の描画まで）で測る。NFR-03 の対象は、IT05-PLAN 3.1 のとおり、登録・個数の変更・削除と、買い物の日付の変更とする。計測の要約の JSON には、実行の開始と終了の時刻、コミット、作業差分の有無、OS・CPU・ブラウザの版、CPU の絞り方を入れる（REV-049 #10 の対応）。計測は 1 つずつ、ほかの計測や Lighthouse と同時に流さない（IT04-RETRO 6 章）。
