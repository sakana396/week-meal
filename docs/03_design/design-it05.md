## 1. 範囲と既存設計との関係

IT05 は、登録行の量を個数か重さで表せるようにし、外部の AI で作ったテキストを貼って一括で登録できるようにする。判定の規則（14 種、70% / 130%、主食の足し方）、目安重量のデータ、色、候補の評価式は変えない。`src/core/` は時刻・DOM・保存先・ネットワークに依存しない（NFR-08）。

| 旧設計 | IT05 の置き換え・継続 |
| --- | --- |
| DES-QTY-02（個数 × 購入時の重さ × (1 − 廃棄率)） | 個数の行は継続。重さの行は DES-QTY-04 で「買うときの重さ × (1 − 廃棄率)」とする |
| DES-SHP-01 の `BasketEntry.count` | `quantity`（個数か重さ）に置き換える。DES-QTY-03 |
| DES-SHP-02 の `register`・`increment`・`decrement` | 1 回押しの登録は継続（新しい行は 1 個）。増減は個数の行だけ。重さの行への 1 回押しは DES-QTY-06。量の直接の指定 `setQuantity` と一括登録 `registerMany` を足す |
| DES-SHP-03、`RegisteredItem.count` | `quantity` を渡し、換算を DES-QTY-04 に寄せる。判定以降は継続 |
| DES-SUG-02〜04 | 候補は「1 単位を足す」まま。既存の行が重さなら、その重さに 1 単位の買うときの重さを足して評価する（DES-QTY-06） |
| DES-STO-10〜12、ADR-0004 | 版 4 に上げる。DES-STO-13、14 |
| DES-UI-20, 21（行の表示・増減） | 行に「個・g・kg」の切り替え、重さの入力、目安の重さを加える。DES-UI-49 |
| DES-PER-03 | 日付の変更の高速化（DES-PER-05）と、新しい操作の計測を足す |

## 2. 量の表し方

### 2.1 量の形（DES-QTY-03）

```ts
type Quantity =
  | { kind: "count"; count: number } // 0.5 刻み、0.5〜999（DES-SHP-02 と同じ）
  | { kind: "weight"; grams: number; unit: "g" | "kg" }; // 買うときの重さ
type BasketEntry = { id: string; foodId: string; displayName: string; quantity: Quantity };
```

- `grams` は常に**整数の g** で持つ。範囲は 1〜100,000 g（100 kg）。`unit` は入力と表示の単位で、計算には使わない。範囲外・整数でない・非有限は受け付けない（エージェントの判断。10 kg の玉ねぎ（E-89）と 2 kg の鶏肉（E-90）を収める）
- g の入力は整数。kg の入力は小数第 3 位まで（g の整数になる値）を受け付け、`grams = kg × 1000` として持つ。kg の表示は `grams ÷ 1000` を末尾の 0 を除いて示す（2,250 g なら「2.25 kg」）
- 新しい行は今どおり `{ kind: "count", count: 1 }` で入る（FR-ING-01、FR-QTY-01）

### 2.2 可食部への換算（DES-QTY-04）

`edibleGrams(food, unitWeight, quantity)` に改める。

- 個数: 既存の DES-QTY-02 のまま。目安重量がなければ 1 単位 100 g の概算（FR-QTY-05）
- 重さ: `grams × (1 − 廃棄率 ÷ 100)`。廃棄率は目安重量の上書き → 代表食品の成分表の値 → 0 の順（DES-QTY-02 と同じ）。目安重量の有無にかかわらず、重さは利用者が入れた値なので**概算にしない**（`approximate: false`）
- 0 以下・非有限は 0 g（既存の規則）

**目安重量の引き方を統一する**（REV-055 #9）: 今は `analyze.ts` と `suggestions.ts` が、食品が手入力でも `displayName` で `unitWeights` を引く。IT05 では、食品番号が `manual-` で始まる手入力の食材は `unitWeights` を引かない（目安重量なし、1 単位 100 g の概算、廃棄率は手入力の値で、ふつうは 0）。分析・候補・目安の表示（DES-QTY-07）・切り替え（DES-QTY-05）のすべてで、`unitWeightFor(food, displayName)` という 1 つの関数で引く。手入力の食材を一覧と同じ名前で覚えていた場合、分析の値が変わる（エージェントの判断。テストで確かめる）。

3 品目の判定（DES-ANL-03）は「量が正の行を数える」とする。感度分析（`analyze.ts` の `sensitivity`、DES-ANL-02）は目安重量の `purchaseG` を factor 倍して目安重量の不確かさを見る仕組みなので、**重さの行は対象にしない**（利用者が入れた重さは目安重量ではないため）。

### 2.3 切り替え（DES-QTY-05、P-08）

行で「個・g・kg」を切り替えるとき、量を次のように引き継ぐ。純粋な関数 `convertQuantity(quantity, to, unitWeight)` にする。1 単位の重さ `u` は目安重量の `purchaseG`、なければ 100 g。

| 元 → 先 | 換算 |
| --- | --- |
| 個 → g・kg | `round(count × u)` を 1〜100,000 g に収める（999 個 × 1,500 g でも 100 kg で止める） |
| g ⇄ kg | `grams` を保ち、`unit` だけ変える |
| g・kg → 個 | `grams ÷ u` を 0.5 刻みに丸め（四捨五入）、0.5〜999 に収める |

換算の結果は目安なので、切り替えた直後に入力欄へ焦点を移し、利用者が直せるようにする。

### 2.4 目安の重さの表示（DES-QTY-07）

個数の行には「1 パック ≒ 250 g」の形で、`unitWeightFor` で引いた `purchaseG`（買うときの重さ、廃棄部分を含む）を示す（FR-QTY-08）。単位は目安重量の `unit`。目安重量がない食材と手入力の食材は「1 単位 ≒ 100 g（概算）」と示す。重さの行には示さない。

### 2.5 量を足すときの規則と上限（DES-QTY-06）

量を足す場面（1 回押しの登録、補う候補、一括登録）は、純粋な関数 `addQuantity(existing, added, u)` で同じ規則にする（REV-055 #5）。

- 種類が同じなら足す。違うときは、足す側を既存の行の種類へ DES-QTY-05 で換算してから足す
- 上限（999 個、100,000 g）を超えるときは**上限で止める**（今の `register` の 999 個の止め方と同じ）。すでに上限なら変えない。戻り値に、止めたかどうか（`clamped`）を返す
- 1 回押しの登録で同じ食材の行があるとき: 個数の行は +1 個、重さの行は +`u` g
- 補う候補（DES-SUG-02）の評価は、今の `min(現在 + 1 単位, 上限) − 現在` と同じく、`addQuantity` で足した後と前の可食部の差を使う。候補を押したときも 1 回押しと同じ結果にする

増減ボタン（±0.5）は個数の行だけに出す。重さの行は数値の入力で変える。`setQuantity(shoppingId, id, quantity)` を reducer に足す。範囲外は何もしない。食材 1 行の削除の取り消し（DES-SHP-02）は `quantity` ごと戻す。

## 3. 保存の版 4（DES-STO-13, 14、ADR-0004 の追記）

### 3.1 形式・移行（DES-STO-13）

形式は `{version:4, shoppings, manualFoods, profile}`。行は `{id, foodId, displayName, quantity}`。`migrations[3]` は各行の `count` を `{kind:"count", count}` に置き換える。版 1〜3 は既存の移行を順に通る。移行は値を変えないので、移行でデータは失われない。

退避（REV-043 #C の対応）: 版の移行の前の原文は、版ごとのキー `weekmeal:state:backup-v<元の版>`（例: `backup-v3`）に退避し、**そのキーがまだないときだけ**書く。一部の破棄（不正な行・不正な買い物を捨てたとき）の原文は、今どおり `weekmeal:state:backup-migration` に書く。これで、版 2 や版 3 の原文が、後の一部の破棄で上書きされない。退避に失敗したら、その起動中の自動保存を止める（DES-STO-10 と同じ）。版ごとの退避は版の数（今は最大 3 つ）しか増えず、それぞれ保存データ 1 つ分の大きさなので、DES-STO-12 の見積もりに「最大で保存データの 6 倍（本体、破損の退避 `backup`、一部の破棄の退避 `backup-migration`、版ごとの退避 3 つ）」として含める。1 つの環境で書かれる版ごとの退避はふつう元の版の 1 つだけなので、実際はこれより少ない。

### 3.2 検査と通知（DES-STO-14）

- `quantity` の検査: `kind` が `count` なら DES-STO-11 の個数の規則（0.5 刻み、0.5〜999）、`weight` なら `grams` が 1〜100,000 の整数、`unit` が `g` か `kg`。余計なキーは持ち込まない。不正な行は捨てて件数を知らせる（既存）
- 捨てた買い物（日付や ID が不正、ID の重複）は、捨てた買い物の件数に 1 と数え、その買い物の中の行は食材の件数に足さない。空の不正な買い物も同じ。今のコードは行の数を足しているので改める。知らせる文は「買い物 N 件・食材 M 件を読み込めませんでした」のように分けて書く（REV-043 #D の対応）
- 一部の破棄の退避に失敗して保存を止めたときは、「読み込めなかったデータを退避できなかったので、保存を止めています。ブラウザの保存領域を確かめてください」のように理由を示す（REV-043 #B の対応）
- 同じ食材の加算（DES-SHP-02 の `register`）では、行 ID の全体の重複を調べない。新しい行を作るときだけ調べる（REV-043 #E の対応）

## 4. レシートの貼り付け（DES-RCP-01〜05、ADR-0006）

### 4.1 画面と遷移（DES-RCP-01）

- 登録画面（`#/register?shopping=<id>`）に「レシートから登録」を置き、`#/receipt?shopping=<id>` に移る。登録先は登録画面と同じ規則（DES-SHP-01、DES-UI-46）で、ホームからなら最新の買い物、履歴の詳細からならその買い物（FR-RCP-01、E-97）
- 買い物が 1 つもないときは、ID なしの `#/receipt` とし、一括登録のときに今日の日付の買い物を作る（DES-SHP-02 の初回登録と同じ。SRS が設計書に委ねた点）
- 画面は 3 段: (1) 指示文とコピーボタン、(2) 貼り付け欄と「読み取る」ボタン、(3) 確認の一覧と「N 件を登録」ボタン
- 貼り付けたテキストは画面の状態だけに持ち、保存しない。外部に送らない（NFR-14）。画面を離れると消える

### 4.2 指示文（DES-RCP-02）

純粋な関数 `receiptPrompt(names: string[]): string` で作る。`names` は、登録の一覧の食材名（`groupFoods(baseFoods.filter(isRegistrable))` の `group.name`。2026-11-02 時点で重複なし 186 件）と、覚えた手入力の食材名（DES-MAN）を、重複を除いて五十音順に並べたもの。指示文には次を書く（文面は実装 Issue で固める）。

1. 添付するレシートの画像から、**食べ物だけ**を書き出すこと。食べ物でない物（日用品など）は書かないこと（E-98）
2. レシートの表記が一覧と違っても、同じ食べ物なら一覧の名前に置き換えること（例: 生椎茸→しいたけ、コマツ菜→こまつな。E-102）。当てはまらない食べ物は、レシートの商品名のまま書くこと（一覧にない物として、確認の画面に名前と件数を出すため。FR-RCP-03）
3. 1 行に 1 品、`食材名,量` の形で書くこと。量は、重さが分かれば `300g` や `2kg`、分からなければ個数（`2`）。量が分からなければ `1`。数字に桁区切りのコンマと分数を使わないこと（4 分の 1 は `0.25`）
4. 説明や見出しは書かず、マークダウンや装飾を使わないプレーンテキストで答えること。コードブロックに入れてもよい（E-102）
5. 食材名の一覧（1 行に 1 つ）

登録一覧 186 件での指示文は 1,316 文字（2026-11-03、手入力 0 件。TC-FR-RCP-02-01）。手入力を足したときの文字数は名前によって変わる。

コピーは `navigator.clipboard.writeText` を使う。使えないときは、指示文を読み取り専用の欄に全部選んだ状態で見せ、「長押ししてコピーしてください」と示す。

### 4.3 読み取り（DES-RCP-03）

純粋な関数 `parseReceiptText(text, catalog)` で、行ごとに次の順で読む。例外は投げず、読めない行は「一覧にない物」として返す。

1. Unicode の NFKC で正規化する（全角の数字・英字・コンマ・括弧を半角にする）。空行（空白だけの行も含む）を飛ばす。NFKC 後に 200 字を超える空行以外の行は、量を読まず元の行を「一覧にない物」として返す（REV-058 の採用済みの提案）
2. 行末の空白と `\` を外す（E-102）。`` ``` `` の行、`#` で始まる行を飛ばす。行頭の `- `、`・`、`* `、`1.` などの箇条の印を外す
3. 数字の間の桁区切り（`1,000`）のコンマを外す
4. 行末の分数 `a/b`（例: `1/4`）は小数に直して個数として読み、`needsCheck` を付ける。数字を含む単位（目安重量の `1/4株` など）の数字の部分は単位の言葉に含めない（`株`・`個` だけを単位の言葉にする）。次に、行末から量を読む。正規表現 `^(.*?)[\s,、\t]*(\d+(?:\.\d+)?)\s*(kg|g|単位の言葉)?$`（大小文字を問わない）で、名前・数値・単位に分ける。単位の言葉は、`unitWeights` の `unit` の値の集合に「個」「つ」を足したもの。合わなければ量なし（個数 1、`needsCheck`）とし、行の全体を名前にする。名前の末尾の区切り（`,`、`、`、タブ、空白）は外す
5. 量の丸めと範囲:
   - 個数（単位なし・単位の言葉）: 0.5 刻みに四捨五入する。0 以下は個数 1 にして `needsCheck`。999 を超えれば 999 にして `needsCheck`。丸めで値が変わったら `needsCheck`
   - g: 整数に四捨五入。kg: `× 1000` して整数に四捨五入。1〜100,000 g の外なら範囲に収めて `needsCheck`
6. 名前を当てる。比べる**両方**（貼った名前と一覧の名前）に、NFKC → `normalizeSearchText`（DES-CAT-06）の同じ正規化をかけ、**完全一致**するものだけを当てる。あいまい一致はしない（ADR-0006）。同じ名前が複数あるときの優先は次のとおり（REV-055 #3）
   1. 登録の一覧の食材（代表食品、DES-CAT）
   2. 覚えた手入力の食材のうち、`manualFoods` の先頭に近いもの（最近覚えたもの。今の `addManualFood` は先頭に足す）
7. 当たらない行は「一覧にない物」として、元の文字列を返す

返り値は `{ candidates: { line, displayName, foodId, quantity, needsCheck }[], unmatched: { line, text }[] }`。同じ食材が複数の行にあっても、この段階ではまとめない。

### 4.4 確認の一覧（DES-RCP-04）

- 当たった行ごとに、登録するかのチェック（初期は全部オン）、食材名、量の欄（DES-UI-49 と同じ「個・g・kg」と入力）を並べる。`needsCheck` の行には「量を確かめてください」と示す
- 食材名は、一覧の食材名と覚えた手入力の食材名から選び直せる（入力欄と候補の一覧。4.3 の手順 6 と同じ当て方で、当たる名前だけを受け付ける）。これで FR-RCP-01 の「食材名と量を確かめて直して」を満たす
- 一覧にない物は「登録しない物 N 件」の見出しの下に、元の文字列を並べる（FR-RCP-03、E-98）。登録はしない
- 「N 件を登録」はチェックした行の数を示す。0 件なら押せない
- 量の欄が不正なら、その行に理由を示し、登録ボタンを押せなくする

### 4.5 一括登録（DES-RCP-05）

reducer に `registerMany(shoppingId, entries, initialShopping?)` を足し、1 回の dispatch で原子的に登録する。`entries` の各行は `{ id, foodId, displayName, quantity }` で、行の `id` は画面が `localId`（DES-SHP-02 と同じ）で作って入れる。reducer は純粋なので ID を作らない。

- 同じ買い物に同じ食材（食品番号と表示名）の行があるとき、または貼った中で同じ食材が先に出ていたとき: `addQuantity`（DES-QTY-06）で足す。このとき渡した `id` は使わない
- ないとき: 新しい行を、貼った量で作る（FR-QTY-01 の例外。FR-RCP-01）
- 新しい行の `id` が全体で重複するときは、その行を登録しない

上限で止めた行があるかは、reducer の結果からは分からないので、画面が dispatch の前に同じ純粋な関数 `planRegisterMany(shopping, entries, …)` で求める（reducer もこの関数を使う）。登録後は登録先の画面（最新ならホーム、前の買い物なら履歴の詳細）に移り、「レシートから N 件を登録しました（登録しない物 M 件、上限で止めた K 件）」を `role="status"` で示す（0 件の項は書かない）。一括登録の取り消しは作らない（確認の一覧で確かめてから登録するため）。

## 5. 行の表示（DES-UI-49）

- 行に量の種類の切り替え（「個」「g」「kg」の 3 つのボタンか、ラジオのまとまり）を置く。今の種類を `aria-pressed` か `checked` で示す
- 個数の行: 今の増減ボタンと個数、その下に目安の重さ（DES-QTY-07）
- 重さの行: 数値の入力欄（`inputmode="decimal"`）と単位。確定（Enter・焦点を外す）で `setQuantity` を dispatch する。不正な値は欄の下に理由を示し、状態を変えない
- タッチの対象は 44 px 以上（IF-05 と既存の行に合わせる）。axe の検査に足す（NFR-06）

## 6. 性能（DES-PER-05, 06）

### 6.1 日付の変更の高速化（DES-PER-05）

IT04 の計測では、CPU 4 倍で 100 行の買い物の日付を変え、最新が入れ替わるときに最大 123.3 ms だった（IT04-RETRO 2 章）。実装 Issue では、まず Chrome の Performance パネルか `performance.measure` で、この操作の内訳（reducer、分析、描画、保存、候補）を測って記録し、主な原因に対して次を順に試す（エージェントの判断）。

1. 買い物ごとの分析を、画面側で覚える。`analyzeShopping` は純粋なので、`Shopping.items` の配列・`manualFoods`・`profile` の参照の組をキーに `WeakMap` で結果を覚える。日付の変更は `items` の参照を変えない（DES-SHP-02）ので、詳細画面で求めた分析をホームでそのまま使える
2. 今は描画のたびに求めている詳細画面の分析（`selectedAnalysis`）を、1 の覚えた結果から引く
3. 保存（`JSON.stringify` と `localStorage`）が主な原因なら、描画の後へ遅らせる（判定の更新の 100 ms には含めない）

判定の規則と表示は変えない。速くした後も、TC-NFR-03-04 の全条件の結果が変わらないことを確かめる。

### 6.2 計測（DES-PER-06）

DES-PER-03 の計測に、重さの入力・量の種類の切り替え・貼り付けの一括登録（30 件）を足すかは実装 Issue で決める。足すなら同じ方法（クリック受信から判定の描画まで）で測る。NFR-03 の対象は、IT05-PLAN 3.1 のとおり、登録・個数の変更・削除と、買い物の日付の変更とする。計測の要約の JSON には、実行の開始と終了の時刻、コミット、作業差分の有無、OS・CPU・ブラウザの版、CPU の絞り方を入れる（REV-049 #10 の対応）。計測は 1 つずつ、ほかの計測や Lighthouse と同時に流さない（IT04-RETRO 6 章）。

## 10. レビューで確かめる点・計画・要求への提案

- **レビューで確かめる点**: 重さの範囲（1 g〜100 kg、整数の g）、手入力の食材で目安重量を引かないこと、重さの行を感度分析から外すこと、重さの行を概算にしないこと、切り替えの換算、版 4 の退避の分け方、指示文の答えの形、完全一致だけで当てること、一括登録で種類の違う行を既存の種類へ換算して足すこと、一括登録の取り消しを作らないこと、性能の対策の順。いずれもエージェントの設計判断であり、本人の発言として扱わない
- **計画への提案**: なし。P-09 の「量の表し方を先に、行の表示と貼り付けはその上に」「持ち越しの小さな修正は別の Issue」を 8 章の A〜F に具体化した
- **要求への提案**: なし。SRS が設計書に委ねた点（FR-QTY-08 の目安重量のない食材の表示、FR-RCP-01 の買い物がないときの入れ先）は 2.4 と 4.1 で決めた。FR-RCP-01 の「食材名と量を確かめて直して」は、食材名を一覧の名前から選び直せることと、量を直せることと解釈した（4.4）
- 指示文で外部の AI が一覧の名前を守るか、レシートの略した商品名をどの程度当てられるかは、AI のサービスによって違い、ここでは確かめていない。本人が使った結果を H-16 で聞く
