# IT05 日付変更の性能計測

対象: NFR-03 / DES-PER-05, 06 / TC-NFR-03-05。

## 根拠と対策

IT04 の実測では CPU 4 倍・100 行・別履歴 100 件の日付変更が最大 123.3 ms だった（[IT04 の記録](performance-measurement-it04.md)）。`Shopping.items` の参照が日付変更で変わらないことを利用し、DES-PER-05 の順 1・2 に従って分析を覚える対策を入れたが、次の実測では 100 ms に達しなかった。

2026-11-03 に Claude Code の手元の PC で、前回の perf コミット `98bf04a`を計測した。CPU 4 倍・100 行・別履歴 100 件の `changeLatestDate` は 5 回で **140.5 / 191.8 / 196.9 / 139.1 / 203.5 ms**。別履歴 0 件でも最大 135.4 ms だった。`test-results/performance-TC-NFR-03-04-TC-NFR-03-05-100行-別履歴100件-CPU4倍-performance/performance-it04.json` の `dateChangeDetail` では、reducer は 2 回とも 0〜0.2 ms、分析の記録はなし（キャッシュ使用）、保存は 14.5〜19.4 ms。reducer の終了から保存開始まで 55〜100 ms の空白がある。空白には React の描画・DOM commit、ブラウザのスケジューリング、その他の同期処理が含まれ、現時点では個別の所要時間を確定できない。最新が入れ替わるため、ホームの 100 行が別の 100 行として描画される。`weekmeal:candidate-initialization` の 28〜48 ms はページ読み込み時のモジュール初期化であり、日付変更クリック後には実行されない。

保存の記録は 14.5〜19.4 ms であり、これだけが主な原因とは確定していない。それでも DES-PER-05 の順 3 にある「保存が主な原因なら」という条件の外で、保存を描画後へ予約した。`ItemRow` にも `React.memo` を加えた。両者の寄与は切り分けていない。最新が別の買い物に入れ替わる場合は行が入れ替わるため、`React.memo` 単独でその描画を省けない。前回の「次に最新となる買い物の分析を先に覚える」処理は、分析の記録がなくても 100 ms を超えたことから、効果が確認できず削除した。判定規則と最終的な保存内容は変えないが、DES-UI-13 の「状態が変わるたびに書き出す」は、短い間の中間状態をまとめて最新だけ保存する形に変わる。未保存分はページを閉じるとき、またはタブが非表示になるときに同期保存する。

## 計測方法と記録

`e2e/performance.spec.ts` の TC-NFR-03-04・05 は、IT04 と同じ各条件を 1 つずつ実行する。日付変更では `dateChangeDetail` に reducer・分析・ホーム／詳細画面の描画開始から DOM commit・保存の開始位置と所要時間を入れる。分析の記録がない回はキャッシュが使われた回である。描画区間の前後には App の処理とブラウザのスケジューリングもあるため、各区間の時刻をクリックから判定描画までの全時間と照合する。候補は判定と別時計で扱う。各条件の `performance-it05-summary.json` に開始・終了の UTC 時刻、コミット、作業差分の有無、GitHub 情報、OS・CPU・Chromium の版、CPU 制限と操作別の全値・最大値を入れる。100 ms 超過は記録し、revision・保存・画面の不整合や計測不能は失敗にする。保存が描画後になったため、保存データの検査前に書き出しを待つ。

計測コマンドは `npm run test:e2e -- --project=performance --workers=1 --output=test-results/performance`。機能 E2E や Lighthouse と同時に流さない。

Claude Code の手元で 2026-11-02T21:06Z（JST 2026-11-03 06:06）から、コミット `5cd7de5`、作業差分なしで `npm run test:e2e -- --project=performance --workers=1` を実行し、19 件成功した。環境は Linux 6.18.54.1-microsoft-standard-WSL2（WSL2）、Intel Core i5-10400F、12 コア、Chromium 156.0.8078.4、表示 360×740、各条件 5 回。CPU 4 倍の `changeLatestDate` の最大値は、100 行・別履歴 100 件で 87.7 ms、100 行・別履歴 0 件で 89.3 ms、30 行で 35.2 / 35.0 ms、3 行で 22.6 / 22.9 ms（順に別履歴 100 / 0 件）。ほかの操作の最大値は 35.3 ms（100 行・別履歴 0 件の `registerLatest`）。全条件が 100 ms 以内だった。Codex 側のサンドボックスでは性能 E2E を実行していない。この時点では今回の可視性と E2E 待機の修正後の値は未実測だった。

同じコミットの機能 E2E は desktop・mobile で 179 件成功、2 件失敗した。両方とも `e2e/manual-memory.spec.ts` の TC-FR-ING-15-07 で、保存直後の読み取りが旧い `quantity.count`（期待 2、実際 1）を取得した。今回、保存済みの値になるまで待つように修正した。この時点では修正後の機能 E2E も Codex 側では未実行だった。

Claude Code の手元で 2026-11-03 JST 06:30〜06:36 に、コミット `64a2fab`、作業差分なしで再計測した。PC・環境は `5cd7de5` の計測時と同じ。機能 E2E（desktop・mobile）は 2 回続けて実行し、各回 181 件すべて成功した。性能 E2E（`npm run test:e2e -- --project=performance --workers=1`）は 19 件成功した。CPU 4 倍の `changeLatestDate` の最大値は、100 行・別履歴 0 件で 82.7 ms、100 行・別履歴 100 件で 83.7 ms、30 行・別履歴 0 件で 35.7 ms、30 行・別履歴 100 件で 37.5 ms、3 行・別履歴 0 件で 20.0 ms、3 行・別履歴 100 件で 21.6 ms。ほかの操作の最大値は 36.1 ms（30 行・別履歴 0 件の `registerLatest`）。全条件が 100 ms 以内で、NFR-03 を満たした。各条件の要約 JSON は手元の `test-results/…/performance-it05-summary.json` にあり、CI の成果物ではない。

Claude Code の手元で 2026-11-03 JST 06:42〜06:49 に、#112 を取り込んだマージコミット `dff991c`、同じ PC・環境で再計測した。指定の検証コマンドはすべて成功し、機能 E2E は 187 件、性能 E2E は 19 件成功した（時間超過は記録のみ）。CPU 4 倍の `changeLatestDate` の最大値は、100 行・別履歴 0 件で **129.3 ms**、100 行・別履歴 100 件で **135.5 ms**、30 行・別履歴 0 件で 78.9 ms、30 行・別履歴 100 件で 51.3 ms、3 行・別履歴 0 件で 22.2 ms、3 行・別履歴 100 件で 25.4 ms。ほかの操作の最大値は 30.6 ms。100 行の条件は `64a2fab` の 82.7 / 83.7 ms から後退し、100 ms を超えた。

100 行・別履歴 100 件の `dateChangeDetail` では、reducer が 0〜0.7 ms、分析が 1.5〜2.8 ms、ホームの描画開始から commit が 46.1〜51.9 ms、保存が 5.8〜8.1 ms（描画の後）だった。クリックから判定描画までの全体は 119.5〜135.5 ms。commit の終了から保存開始まで約 60 ms の間隔がある。`#112` により各行に入力欄・単位切り替え・目安表示が加わり、日付変更でホームの 100 行すべてが別の行に入れ替わる。このため、行の DOM のレイアウトと描画が後退の主因と考えられる。ただし約 60 ms の間隔の内訳は計測されておらず、ブラウザのスケジューリング等との寄与は未確定である。詳細の記録は手元の `test-results/performance-TC-NFR-03-04-TC-NFR-03-05-100行-別履歴100件-CPU4倍-performance/performance-it04.json` にある。

今回、画面外の `.item-row` に `content-visibility: auto` と推定寸法を適用し、行内の目安重量の重複検索と量のキーの重複生成を減らした。100 行でも画面に表示される行は一部なので、ブラウザが画面外の行のレイアウトと描画を遅らせる効果を見込む。行の React 要素と DOM 自体は作るため、46.1〜51.9 ms の commit 全体を省くものではない。焦点移動・スクロール・可視性・モバイルの横幅は TC-NFR-03-05 の E2E に確認を追加した。この対策後の性能値と E2E の結果はサンドボックスでは**未実測**であり、100 ms 達成は未確認である。

## 新しい操作の扱い

重さの入力・量の種類の切り替え・貼り付け 30 件は、NFR-03 と IT05-PLAN 3.1 が定める操作に含まれないため、TC-NFR-03-05 には追加しない。これらを診断用に測る場合は、画面実装が揃った後に別 Issue で扱う（DES-IT05 8 章）。
