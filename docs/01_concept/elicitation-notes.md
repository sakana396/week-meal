## 2. 製品の狙い

| # | 発言の要旨 | 解釈 |
|---|---|---|
| E-03 | 「簡単入力のみで管理する」を目標にする | 最上位の目標。入力の手間を最小にすることが、ほかのすべてより優先される |
| E-04 | スコープは自炊 | 外食・コンビニ食・中食は対象外 |
| E-05 | 既存アプリは外食・コンビニ食に注目している | 競合との差別化の軸は「自炊」 |
| E-06 | そのため既存アプリは 1 食ごとの入力になる | 1 食ごとの記録は、本アプリが避けたい手間の典型 |
| E-07 | このアプリは自炊による簡単入力を目標にする | E-03 と E-04 の組み合わせ |
| E-08 | 自炊の場合、複数日分の食材をまとめて購入する | 入力の単位は「食事」ではなく「買った食材」 |
| E-09 | そのため、栄養の偏りがあるかの判断だけをする | 出力は摂取量の正確な管理ではなく、「偏りの有無」の判定に絞る |
| E-10 | 量の判断はテキトーでよい。入力は 100g ではなく「1 つ」のようにする | 量は個数（1 本、1 玉、1 パックなど）の概算で入力する。グラム入力は求めない |
| E-11 | 割合で栄養を書くことで、何日分であっても大丈夫にする | 栄養は絶対量ではなく割合（バランス）で表す。何日分の食材かを入力しなくても判定が成り立つ |

## 3. 既存の画面設計メモ（docs/screen-design.md ほか）から

本人が先に書いていたメモ。あくまで参考で、SRS と食い違う部分は SRS を優先する（E-45）。

| # | メモの要旨 | 解釈 |
|---|---|---|
| E-20 | ホーム画面は、登録した食材だけで栄養のサマリを表示する。食品データベースの食品は混ぜない | 集計の対象は「自分が登録した食材」だけ |
| E-21 | 食品一覧画面で、文科省データの食品を検索・表示する。ホームとは分ける | 食品データベースの閲覧は補助機能 |
| E-22 | 食材登録では、一般的な食材名を 1 回押すだけで登録を完了する。状態・部位・量は通常の登録時に選ばせない | 登録は 1 タップ。量は登録時には聞かない（個数の初期値で登録し、後から直す） |
| E-23 | 手入力で食材を登録できる。カテゴリはスーパーの棚から選ぶ | データベースにない食材の逃げ道 |
| E-24 | 栄養詳細画面で、基本栄養素からビタミン・ミネラルまで表示し、足りない栄養素を強調する | 偏りの判定結果の見せ方 |
| E-25 | 不足の強調は、基準値をどこから持つかを決めてから実装する | 基準値の出典は未決 |
| E-26 | 入力モードは「簡易」（初期状態、代表データで登録）と「詳細」（文科省の正式名称・状態・食品番号から選ぶ）を切り替える | 簡単さを守りつつ、こだわりたいときの逃げ道を残す |
| E-27 | 文科省の食品は一般的な食材名にまとめて表示し、生・ゆで・焼きなどは原則「生」の代表データを使う。栄養が大きく違い、スーパーで別の商品とされる物（から揚げ、漬物、缶詰など）は別項目にする | 表示名のまとめと代表食品の規則（docs/data-design.md） |
| E-28 | 食材はスーパーの棚（野菜、果物、魚、肉、卵、豆腐・納豆、乳製品、米・パン・麺、惣菜、冷凍食品、飲み物、お菓子、調味料、その他の 14 種）で絞り込む。未検索時はスーパーでよく見る食材を先に出す | 栄養学の分類ではなく、売場の感覚で探せるようにする |
| E-29 | 将来はレシートを撮影して、まとめて登録できるようにしたい。レシートで分かるのは「買ったもの」で「食べたもの」ではないので、摂取カロリーや栄養不足とは断定しない | 簡単入力の発展形。表示の言い回しにも制約がかかる |
