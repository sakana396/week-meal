## 2. 判定の仕組み（コードの確認）

3c4ba3e の `src/core/analyze.ts` の `analyzeBasket` と `src/core/nutrition.ts` を読んで確かめた。

1. エネルギーのデータがある食材が 3 品未満なら判定しない（`minimumItemCount = 3`、`insufficient`）。
2. 登録した食材の可食部の栄養を合計する（主食を除く合計。`sumNutrients`）。
3. 主食を、主食を除くエネルギー × 割合 ÷ (1 − 割合) の量だけ足す（`stapleItem`）。割合は `stapleShares`（小 30%・中 40%・大 50%。E-37）。主食が全体のエネルギーの 30〜50% になる。
4. 主食を足した合計から PFC 比を求め（`nutrientRatios`・`pfcRatio`）、炭水化物の割合を目標 50〜65%（`dietaryReference.ts` の `carbohydratePctRange`。E-38）と比べる。下回ると不足（`low`）。PFC 比は、たんぱく質・脂質・炭水化物の量に 4・9・4 kcal/g を掛けた合計に対する割合で、食品データのエネルギーの値とは別に求めている。

主食はエネルギーで一定の割合を占めるように足されるので、ほかの食材の炭水化物が少ないほど、全体の炭水化物の割合は主食の分に近づく。主食だけで何 % になるかは、今回は計算していない。下の表の値は、アプリのコードで求めた。

### 3.2 結果

### 3.3 読み取れること

- 例 4 と例 5 は品数が同じで、豚肉の量だけが違う。豚肉を増やすと普通盛りでも不足になった。品数そのものではなく、炭水化物の少ない食材（肉・卵）がエネルギーの多くを占めるかどうかで判定が変わる
- 品数が少ないと 1 つの食材の割合が大きくなりやすく、本人の観察（E-137）と同じ向きの結果になる。ただし、本人が試した食材と量は分からないので、本人の観察を説明できたとまではしない
- アプリは登録した食材を、その期間の食事のすべてとして計算する（主食だけは設定で足す）。家にある食材や、登録しなかった食材は数に入らない。少しだけ登録したときの判定は、実際の食事の偏りより、登録した食材の偏りを示す

### 3.4 調べなかったこと

- 本人の実際の買い物での再計算（TC-FR-BAL-02-08）: データを受け取っていない
- 境界付近の入力での丸めの比較（TC-FR-BAL-02-09）: 本人の実際の入力がなく、上の例にも境界付近の値がない
