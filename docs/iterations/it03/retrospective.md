## 2. 仮説の検証結果

### H-09 手入力した食材の 2 回目からの登録が登録画面で 1 タップか（達成）

覚えた食材は、登録画面の一覧で 1 回押すと登録できる。ホームからはタブ「登録」→ 食材名の 2 タップ（TC-FR-ING-15-04、E2E）。

### NFR-03 判定の更新まで 100 ms 以内か（未確認）

「中位のスマートフォン相当」の条件が決まっていないので、達成は確かめていない。参考の計測値（3・30・100 行 × CPU 1・4 倍、各 5 回。CPU 4 倍は Chrome の模擬）は次のとおり（REV-037）。

| 実行 | 最大 | 100 ms を超えた回 |
|---|---|---|
| Claude Code の手元（WSL2）1 回目 | 73.8 ms（100 行・4 倍・個数の変更） | なし |
| レビュアーの手元（同じマシン） | 約 73 ms（100 行・4 倍） | なし |
| Claude Code の手元 2 回目 | 247 ms（100 行・4 倍・候補の登録の 1 回目。残り 4 回は 75〜93 ms） | 1 回 |
| CI（GitHub Actions、AMD EPYC 4 コア） | 78 ms（100 行・4 倍・使い切った） | なし |

補う候補の計算（ADR-0005 の予算 50 ms）は、レビュアーの実行で 1 回 57.8 ms と予算を超えた。Claude Code の手元 2 回目では最大 48.5 ms。

### NFR-04 Lighthouse のモバイルの Performance スコア（記録した）

2026-10-25 に、Claude Code が Lighthouse 13.5.0 の CLI で 3 回測り、3 回とも 98 だった（モバイル、simulate の制限は CPU 4 倍・RTT 150 ms）。開発者の PC の WSL2 で、Playwright の Chrome（156.0.8078.4）を headless で使った。手順書は DevTools での計測を想定していたが、CLI で代えた。実機ではなく、保存データのない初回表示だけを測った。記録は `docs/04_test/performance-measurement-it03.md`、レポートの JSON は `docs/04_test/lighthouse-it03/`。NFR-04 は目標値を設けないので、記録したことで TC-NFR-04-01 を満たす。

### H-07 不足を色で見せると「どのくらい足りないか」が分かるか（達成。本人の感想）

不足は充足率 0% で赤、100% で黄の連続した色にした（50% で橙 `#ff8000`）。不足は 70% 未満だけなので、PFC 以外の栄養素は赤〜橙（`#ffb300` 付近）までしか出ない（REV-027 #3）。

本人の感想（2026-10-26、E-57・E-58）: 「不足の色ちょうどいい」「過剰もスケールさせてみるといいかもしれないな」。過剰の程度でも色を変える案は IT04 の候補（E-63）。

### H-08 ホームの補う候補が、実際に買ってもよい食材か（おおむね達成。本人の感想）

本人の感想（2026-10-26、E-59）: 「いいのがでてる」。ただし「魚が出るとき、さかなやなーとなる。別の種類（野菜、肉）での場合もあれば嬉しい」。候補が同じ種類に偏るので、棚の違う候補も出す案は IT04 の候補（E-63）。

IT03 で増えたほかの操作（削除の取り消し、手入力の改善）は「全部問題なかった」（E-60）。

使ってみて、「使い切った」は使い道がなく、登録した食材を日付つきの「買い物」にまとめ、最新の買い物だけで判定する形がよいという意見があった（E-61・E-62）。要求の変更になるので IT04 の計画で扱う（E-63）。

## 6. 良かったこと・困ったこと

- 良かったこと
  - 依存のない Issue を main から並べて作った（P-09）ので、IT02 のような積み上げの付け替えはなかった。衝突は traceability・テスト仕様書の末尾の行がほとんどで、両方を残して解消できた
  - 実装（Codex）・コミットとマージ（Claude Code）・レビュー（別のサブエージェント）を分けた。レビューで、ホームの判定の枠が赤くなる（PR #68）、検索語が空でも「この名前で手入力」が出る（PR #71）、計測の結果がファイルに残っていない（PR #73）など、E2E では見つからなかった不具合が見つかった
  - 補う候補の性能を設計の段階で見積もってもらい（REV-027 #2）、差分計算にしたので、候補の計算はおおむね数十 ms に収まった
- 困ったこと
  - Codex のサンドボックスでは E2E（localhost）を動かせない。ネットワークを許可して起動しようとしたが、実行環境の安全装置に止められた。E2E は毎回 Claude Code が実行し、失敗すれば Codex に戻したので、往復が増えた（PR #67、#70、#71、#72、#73）
  - Codex は、E2E を実行していないことを文書に「Claude Code が実行する」「確認待ち」と書きがちで、レビューで何度も直した。Claude Code が Codex に渡す依頼文のひな形（作業用の一時ファイル）に、実行の予定を文書に書かないことを足した。リポジトリの手順書（AGENTS.md、SKILL.md）は変えていない
  - 複数の worktree の E2E が同じポート 4173 を使うので、同時に動かすと失敗した。マシンの負荷が高いと時間切れも出た。実行の前にポートの空きを確かめるようにした（Claude Code とレビュアーへの依頼文で伝えた。リポジトリの手順書は変えていない）
  - Claude Code が振り返りの初版に、Lighthouse を「この環境では動かせない」と、試さずに書いた。レビューで指摘され（REV-038 #1）、試すと CLI で計測できた
  - Claude Code が PR の説明に、1 回の実行の計測値を「予算に収まった」と言い切って書いた。レビュアーの実行では予算を超える回があり、説明を直した（REV-037）。計測値は複数回・複数の環境の値をまとめて書く
- エージェントの作業
  - 2026-10-25 の本人の指示で、Codex はコミットせず、Claude Code が差分を読んでコミットするようにした（PR #64、REV-028）
