# ADR-0002: 食品データの絞り込みと目安重量の形式

- 状態: 承認待ち
- 日付: 2026-10-14
- 根拠: SRS-001 FR-FDB-01〜03、FR-QTY-02〜05、NFR-11、QA-09、E-13、E-42〜44、PLAN-001 P-04

## 背景

- 現在の `src/data/foods.json` は成分表の全 2,538 件（約 3.2 MB）を持つ。自炊で使わない食品（アーティチョークなど）が大半で、登録の一覧が長く、転送量も大きい（E-42, E-43）
- 個数から重さを求めるために、食材ごとの単位と目安重量が要る（FR-QTY-02）。成分表には個数あたりの重さはないが、**廃棄率**（REFUSE 列）はある
- 成分値は原典から書き換えない（CST-01）

## 決定

### 1. 絞り込みは食品番号の一覧で定義する

- 絞り込みの定義は `scripts/food-selection.json` に置く。中身は食品番号と、読みやすさのための正式名称の組の配列とする
- 変換スクリプト `scripts/convert-mext-foods.py` は、成分表の Excel を読み、定義に含まれる食品だけを `src/data/foods.json` に書き出す
- 食品を足すときは、定義に食品番号を 1 行足して変換し直す
- 定義の初版は、よくある食材（`supermarketFoods.ts`）を起点に、自炊でよく買う食材名を 150〜250 個選び、それぞれの食材名にまとまる食品（生・ゆで・焼きなどの状態の違いを含む）をすべて入れる（P-04）
- 主食の代表食品（ご飯・パン・麺）は、登録の一覧には出さないが、主食の計算のために含める

### 2. 廃棄率を食品データに加える

- 変換時に REFUSE 列を `refusePct`（%、数値または null）として出力する

### 3. 目安重量は「購入時の 1 単位の重さ」で持つ

- `src/data/unitWeights.ts` に、食材名（登録の一覧の表示名）ごとに `unit`（本・玉・パックなど）と `purchaseG`（購入時の 1 単位の重さ。皮や芯を含む）を書く
- 可食部の重さは `purchaseG × (1 − 代表食品の refusePct ÷ 100)` で求める
- 購入時の重さは、店頭で目にする重さに近く、利用者が査閲しやすい。可食部への換算は成分表の公式の廃棄率に任せる
- 各値の出典（または「概算」であること）を同じファイルのコメントに書く（QA-09）

### 4. 定義データの整合性はテストで検査する

- 絞り込みの定義・表示名・棚・目安重量が、食品データに存在する食品番号・食材名だけを参照していることを、Vitest のテストで検査する（NFR-11）

## 理由

- **食品番号の一覧は誤りにくい**: 名前の部分一致で絞り込むと、似た名前の別の食品が混ざる（data-design.md と同じ理由）
- **変換スクリプトは Python のまま**: Excel の読み込みはすでに動いている。表示名のまとめ（TypeScript）とは食品番号でつなぐので、二重実装にならない
- **購入時の重さ＋公式の廃棄率**: 可食部の重さを手で書くより、根拠を分けて説明できる

## 検討した代替案

| 案 | 採用しなかった理由 |
|---|---|
| 全件を同梱し、画面側で絞り込む | 転送量が減らない。一覧を出さない食品の成分値を持ち続ける理由がない |
| 食材名（表示名）で絞り込みを定義する | 表示名のまとめ方を変えると、絞り込みの結果が知らないうちに変わる |
| 可食部の重さを直接書く | 根拠が説明しにくく、査閲もしにくい |

## 影響

- 成分表の Excel を取り直す手順は README のまま。変換コマンドに定義ファイルの引数が加わる
- 詳細モード（FR-ING-07）と食品一覧（FR-UI-08）も、絞り込んだ食品だけを扱う
